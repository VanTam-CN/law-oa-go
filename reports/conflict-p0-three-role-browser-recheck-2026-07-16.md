# 律所三角色利益冲突检查浏览器复验记录

**日期**：2026-07-16
**环境**：本地受控 QA（前端 `http://127.0.0.1:3003`，后端 `http://127.0.0.1:8080`，PostgreSQL、Redis、Elasticsearch 已启动）
**依据**：`docs/利益冲突/conflict-p0-law-firm-trial-spec.md`、`pd-01-to-07-decision-draft.md`（本地决策草案）
**性质**：面向真实律所使用习惯的仿真验证，不是生产放行签字。所有业务数据均为虚构或脱敏数据。

## 1. 验收视角与测试工具

本轮按“不会 IT 的律所使用者”设计路径，不从接口名称或数据库字段倒推操作。每个角色只处理自己工作中会遇到的任务，并验证按钮名称、状态说明、下一步入口和权限边界。

- **律师 A**：接待新客户、准备新案、运行冲突检查，查看自己能看到的最小结果。
- **律师 B**：处理与 A 无关的独立案件，并主动尝试查看 A 的案件、客户和冲突任务。
- **冲突核查人 C**：查看全所冲突任务、完整命中证据、复核记录和豁免条件。
- **Chrome Computer Use**：检查真实 Chrome 窗口、登录后的工作台、导航菜单和可访问性树。
- **浏览器 DOM 验证**：使用页面可访问结构完成确定性点击、路由和文案断言；控制台错误单独记录。
- **工程验证**：Go 定向测试、Go 构建、前端类型检查和生产构建。

本轮未使用真实客户名称、真实案件材料、身份证号或统一社会信用代码。

本报告同时保留了前序三角色复验结果，并追加本轮真实浏览器续测。凡是由 Computer Use 会话异常导致的未观察项，均单独标注为“证据缺失”，不作 PASS 或 FAIL 推断。

## 8. 放行判断

### 本轮已经有证据支持

- 待处理案件详情能告诉律师下一步是利益冲突复核。
- 冲突页默认是清单，不会在无上下文时自动打开错误详情。
- 覆盖不足或主体信息不完整时不会显示“无冲突”安全结论。
- 普通律师和冲突核查人的证据可见范围已经分开。
- 新建/补充检测结果会显式写回案件，案件、检测任务和冲突审批不会再依赖标题猜测关联。
- PostgreSQL 本地升级库已完成到迁移 65，且不是 dirty 状态。
- 律师 B 的案件、客户、主档案和已知 A 任务的直接访问被服务端拒绝。
- 受限详情不再泄露历史案号、标题、任务编号或原始证据。
- 前端重复 key 警告已修复，构建与定向回归通过。

### 仍不能作为生产发布依据

1. 旧数据仍可能缺少规范化检索主体快照；这会影响冲突核查人对历史证据的完整判断，必须在真实导入前完成数据治理。
2. 当前 QA 的冲突检索范围仍是 `COVERAGE_LIMITED`；权威档案来源、关联方覆盖和缺口处置尚未由律所确认，不能把本地演练结果当成全所“无冲突”。
3. 主体版本变更的服务端门禁已有实现和定向测试，但发函、立案、出法律意见、签章等每类受控对外动作尚未完成完整浏览器/API 证据链。
4. PD-01 至 PD-07 仍是草案；例外审批、独立核查人、身份数据保护、豁免和保留期限必须由律所签署后才能配置。
5. 本轮 Computer Use 在发起审批后丢失正文可访问树，审批详情页的人工视觉证据缺失；22 条 Playwright E2E 仅证明前端 mock 流程，不替代真实浏览器复验。

**结论**：本轮仿真证明案件到冲突清单、检测详情、最小披露和冲突审批的核心链路正确，普通律师不会因“存在受限命中”而误以为无冲突；但由于检索覆盖尚未完成律所确认、历史数据治理和审批详情人工证据仍有缺口，当前版本仍应定位为“可继续受控验收”，不能宣称已经满足真实律所生产发布条件。
