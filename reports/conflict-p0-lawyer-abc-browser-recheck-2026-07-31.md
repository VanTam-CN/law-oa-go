# 利益冲突三角色真实浏览器复验记录

日期：2026-07-31  
环境：本地非生产 PostgreSQL QA 环境，虚构数据  
角色：律师 A、律师 B、独立冲突核查人 C

## 1. 复验目标

验证利益冲突流程是否符合普通律师的实际操作习惯，并重点检查：

- 律师只能看到自己案件所需的信息；
- 受隔离历史事项不会通过列表、详情、审批或直接 URL 泄露；
- 独立核查人能看到并处理分配给自己的冲突审批；
- 自动检索、人工复核和最终接案决定不会混成同一个结论；
- 拒绝、退回和同意不会因误点立即生效，并留下可回看的事实依据；
- 1366px 和 390px 视口下页面无横向溢出或关键按钮遮挡。

## 2. 使用的虚构数据

- 律师 A：`qa.lawyer.a@qa.invalid`
- 律师 B：`qa.lawyer.b@qa.invalid`
- 核查人 C：`qa.conflict.officer@qa.invalid`
- A 案：`QA-P0-A-2026-001`
- B 隔离案件：`QA-P0-B-2026-001`
- 冲突检测：`QA-P0-A-CHECK-20260719`
- 冲突审批：`APR-QA-P0-20260719`

仓库和报告未记录测试密码、真实身份证号、真实统一社会信用代码或真实客户资料。

## 4. 本轮发现并修复

1. 冲突核查人能看到待办数量，但审批路由要求管理权限，无法进入处理。
2. 工作台没有把既有冲突审批 ID 回传给冲突任务，详情可能重复创建审批。
3. 普通律师可能看到机器风险分数并将其误认为最终结论。
4. 案件 `priority` 和审批 `priority` 被界面写成“风险”。
5. 宽屏风险摘要存在内容相互挤压，窄屏侧栏占用正文宽度。
6. 点击“拒绝”会立即提交，没有二次确认，也不要求填写依据。
7. 审批终态清空当前审批人后，原核查人失去回看权限。
8. 审批详情未加载审批记录，处理依据无法核对。
9. 同一处理依据在“意见记录”和“审批记录”重复显示。
10. 只读申请人被错误提示可以选择“退回修改”。
11. 审批工作台向普通用户显示毫秒级加载耗时。
12. 工作台与冲突页的新布局缺少共享样式，出现散乱文字和大面积空白。
13. 待办中心菜单仍指向“暂不可用”页面。
14. 登录页默认长期保存令牌，并把登录响应写入浏览器控制台。
15. 无权访问指定冲突任务时只显示空清单，普通用户不知道是无数据还是无权限。
16. 审批重新提交后，历史拒绝记录与本轮“已提交”状态缺少周期说明。
17. 1280/1366px 宽度下审批正文被二次分栏，处理依据被挤成逐字竖排并裁切。
18. 成案后主体变更的搜索接口直接查询全所主体表，律师可能通过名称或曾用名枚举只存在于其他案件、包括隔离案件中的主体；保存变更时也可伪造主体编号绕过下拉搜索。现已改为仅返回当前案件或当前账号可访问案件中的主体，并在服务端再次校验新增、替换和移除引用。律师、主任、隔离白名单及伪造编号的反向测试均已覆盖。
19. 真实案件出现主体库中从未登记的新对方时，原界面只能提示联系核查岗，流程无法闭环。现已增加律师提报全新主体、专用密钥加密身份标识、核查岗队列、规范化身份摘要去重、新建/合并/驳回、双人回避和统一待办；登记待确认期间案件持续阻断。浏览器 E2E 用例已编写，当前运行因本地浏览器工具额度限制尚未取得执行结果，不计作已通过证据。
20. 生产 PostgreSQL 曾对 `case_subject_revisions` 安装禁止任何 UPDATE 的只追加触发器，与主体重检必须推进状态的实现矛盾；SQLite 测试无法发现。迁移 `000069` 已将其替换为状态保护触发器：禁止删除、关键字段不可变、只允许 Spec 白名单状态迁移，候选载荷仅允许在核查岗确认登记时替换。生产 bootstrap 与就绪结构检查同步要求新触发器。
21. 初次接案此前只保存对方名称，冲突服务读取不到结构化身份，且新增证件字段一度会进入浏览器草稿和接口响应。现已增加迁移 `000070`、客户及对方身份前置门禁、服务端加密和规范化检索；浏览器草稿排除身份原文，接口只返回受保护登记状态。后端定向测试及前端类型、Lint、单元测试已通过；Chrome E2E 尚未执行，不计作浏览器通过证据。
22. 企业客户的统一社会信用代码曾复用名为 `id_card` 的保护字段，导致主体索引和部分冲突路径把企业标识错误标注为 `ID_CARD`。现已增加迁移 `000071` 和客户通用身份契约，主检索、主体索引、案件重检、后台扫描及 QA 夹具统一按明确身份类型处理；旧字段仅保留兼容回读。Chrome E2E 尚未执行，不计作浏览器通过证据。
23. 新建客户若未填写可选邮箱，第二条记录会撞上空字符串唯一索引；创建成功后，列表可见但客户主档案仍按案件归属拒绝访问。现已增加 `000072`、`000073`，将创建人纳入首案前对象权限、空邮箱保存为 `NULL`，并保证隔离墙优先于创建人权限。真实浏览器已验证客户创建、立即可见、主档案打开和联系人更新。
24. 冲突引擎把 `COVERAGE_LIMITED` 同时写成 `has_conflict=true`，导致“0 个命中”的记录在清单和详情中显示为“存在受限命中”。现已把实际命中与接案门禁分离：无证据覆盖受限记录显示“未发现匹配记录，但检索范围受限”，仍禁止提交；真实受限命中继续隐藏历史案件明细。真实浏览器已验证清单、详情和审批快照文案一致。
25. 冲突审批摘要曾把当前对方当事人误称为“历史主体”，审批表的无时区字段还导致浏览器将审计时间多加 8 小时。现已按是否存在匹配证据切换为“检索对方/历史主体”，并通过 `000074` 将审批域审计时间转换为 `timestamptz`；生产 schema 门禁会拒绝未迁移的审批审计时间字段。真实浏览器复验显示申请时间、审批记录时间与实际操作时间一致。
26. 侧栏 CSS 在 1024px 已缩为图标栏，但 React 到 900px 才更新折叠状态；手机侧栏移出屏幕后正文仍可能保留侧栏偏移。现已统一 1024px 平板折叠和 768px 手机零偏移规则，并新增 960px、640px 布局 E2E；宽屏、平板、小窗口和手机均无页面级横向溢出。
27. 客户主联系人曾复用客户公共邮箱、电话和备注字段，连续编辑会污染客户主档案。现已增加 `000075_client_primary_contacts`、对象权限校验、乐观锁和用途隔离加密；真实浏览器及数据库只读核验确认联系人可持久化，客户邮箱/备注不变，数据库密文不含电话或邮箱明文片段。
28. 新建客户后详情未自动切换，客户页的“发起冲突检查”也未说明会先建立接案草稿。现已自动选中新客户并回到基本信息页签，入口改为“以此客户新建立案并检查冲突”；内置浏览器已验证客户上下文正确带入。
29. 律师接案结果在“范围受限、待人工复核”的同时仍显示机器评分 `0`，容易被理解为零风险。现已从律师接案页和覆盖受限清单删除机器风险与分数，只保留处置状态、覆盖边界和“自动检索不能替代独立人工复核结论”；检测详情继续明确显示“暂不评分”。
30. 审批快照未保存案件类型，前端缺值时默认显示“商事”，导致本次民事接案在审批页变成商事。现已把原始 `case_type` 写入冻结快照，旧审批从冲突记录兼容回读，且取消任何业务类型默认值；内置浏览器已验证接案与审批均显示“民事”。
31. 审计折叠入口会被页面刷新重置，表现为按钮可见但点击无反馈。现已取消该无效交互，将少量检测编号、来源、匹配方式和审批读取记录作为次要信息默认展示；审批读取耗时按接口名称去重，只保留最近一次。
32. 1280px 常见办公屏宽度下，审批详情仍保持三栏布局，而“申请信息”内部再分两列，客户、案件和对方名称被压成逐字换行。现已在 1400px 以下将申请信息改为单列并缩短标签列，内置浏览器截图确认长名称可横向阅读；新增 1280px 文本宽高回归用例。
33. 生产门禁要求双人批准政策，但此前只有数据库表和运维文档，不会 IT 的主任/合规负责人无法完成登记。现已增加 `000076`、不可修改材料包、分责确认记录、服务端双人独立校验和“冲突治理”页面；技术管理员、普通律师均不能进入或代签。
34. 主任与合规账号登录后默认进入工作台，但前端权限回退漏掉这些业务角色，首屏显示“无权访问”。现已补齐 director/partner/management/compliance/risk/risk_control 的工作台权限，并保持技术管理员不能进入专业冲突治理。
35. 冲突治理初版直接显示 `CASE_ARCHIVE` 等英文代码和完整索引哈希，且日期不显示年份，跨年复核日期看起来相同。现已改为中文档案名称、业务化对账状态、完整年月日，并显示管理确认人与合规确认人姓名。
36. 本地 QA 种子只有律师 A/B 和核查人，无法验证管理/合规双签。现已增加完全虚构的管理合伙人和合规负责人账号；密码仍只由运行时 `QA_PASSWORD` 提供，不写入仓库或报告。
37. 权威档案来源只有后端接口，非技术核查岗无法登记同步、覆盖率、重复率、质量复核与告警证据。现已在“冲突治理”提供四类中文来源的登记/更新表单，百分比由页面转换为基点，索引运行编号仍强制绑定导入对账报告。
38. 数据质量责任人初版要求手填账号编号。现已改为按姓名和部门选择，服务端仍只接收受控账号 ID。
39. 通用只读显示函数曾把档案表单的空缺口转换为“未填写”并提交，导致看似空白却被服务端判断为存在缺口。现已严格区分显示占位与表单值，空值不再进入合规证据；浏览器沿原表单保存成功。
40. 核查岗无权查看政策包，但页面指标曾显示政策数量为 0，容易把权限遮罩误认为业务状态。现已对核查岗隐藏政策数量和双签指标，仅展示其职责内的权威来源覆盖与登记操作。

以上问题已完成代码修复。2026-08-03 已使用内置浏览器补充验证 `000070`、`000071` 的初次接案身份输入、客户通用身份展示、正式冲突检查、覆盖受限门禁和独立冲突审批；自动化 E2E 仍须在最终发布流水线完整重跑。

## 5. 部署环境发现

- 本次本地数据库包含此前演练遗留的冲突记录。该库只能用于开发回归，生产部署必须使用空白数据库按迁移初始化，再导入经核验的权威档案。
- 应用现已默认仅在当前浏览器会话保存登录状态，“记住我”默认不勾选；但 Chrome 密码管理器仍可能自动填充历史密码。共享电脑必须使用独立操作系统账号或独立浏览器配置，并由律所策略禁止保存业务账号密码。
- 生产就绪检查现在要求存在一份处于有效期内、管理负责人和合规负责人分别批准的正式政策配置；缺失、过期或同一人双重批准时服务拒绝通过就绪检查。
- 权威数据源必须提供同步时间、字段覆盖率、重复率、质量复核人、告警与更正流程证据。证据过期或指标未达标时，冲突检索范围按不完整处理并阻断接案。

## 7. 放行边界

本轮证明了三角色界面流程、对象权限、隔离展示、审批决定和审计回看的实现可用，但不能单独证明系统已经可以处理真实客户资料。真实客户上线仍必须完成：

- 律所权威档案源已全量导入并完成覆盖率证明；
- 未导入纸卷、转入档案和律师个人前客户清单已进入缺口台账；
- 成案后主体变更强制重检状态机及对外动作门禁已在后端验收；
- 隔离墙对搜索、聚合、导出、通知和直接 API 的全表面验证；
- 身份标识采集、加密、密钥托管、保留和销毁制度已经律所确认；
- 律所指定核查人、代理人、豁免审批人及双人复核规则已落地。
- 新主体登记代码闭环已实现，但仍须在可启动 Chrome 的环境运行新增两角色 E2E，并以真实权限配置验证登记核查人和最终冲突复核人确为不同且无直接管理关系，完成前不得据此单项宣布真实客户上线。
- 正式政策配置由律所两名不同责任人签署并录入，生产就绪检查通过。
- 使用全新生产数据库，演练账号、演练案件及历史测试记录均未进入生产环境。

因此当前结论为：可以继续受控虚构数据试用；在上述组织和数据门禁没有书面闭环前，不应直接录入真实客户案件。
