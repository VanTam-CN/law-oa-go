# Law OA Go 小律所真实浏览器基准测试报告

- 测试日期：2026-08-12（Asia/Shanghai）
- 测试对象：本地开发运行态，前端 `http://localhost:3003`，后端预期 `http://localhost:8080`
- 浏览器：ego-browser 隔离 Chromium 任务空间
- 结论口径：当前运行态、小律所受控试用与生产放行分别判断
- 数据边界：仅使用 README 所列匿名演示账号和虚构输入；未创建案件、客户或审批数据，未上传文件，未触发通知，未删除数据

## 1. 执行摘要

**当前运行态结论：NO-GO，不适合交给小律所做受控试用，更不能录入真实客户案件。**

直接原因不是页面打不开，而是后端 `:8080` 没有监听。前端 Vite 已能访问，但所有登录和 API 请求都被代理立即返回 HTTP 500。律师、助理、财务三个 README 演示账号均无法登录，因而登录后的客户、接案、冲突检查、案件、审批、文档、财务、收件箱等流程全部属于“未验证”，不能视为通过。

同时存在两项环境级放行阻断：

1. 现有本地数据库的 `schema_bootstrap_state` 是 `postgres-mvp-2026-07-19-v4`，当前源码要求 `postgres-mvp-2026-08-05-v13`，存在明确版本漂移。
2. 本地数据库仍有 11 个 active 的 `@example.test` 演示账号；按当前 readiness 规则，这会阻断生产就绪。

登录前表面质量并非全盘失败：未登录深链保护、桌面和移动端响应式、密码管理器 autocomplete、在途防重复提交均通过。但这些优点不足以抵消认证入口完全不可用。

## 2. 测试方法与证据边界

### 2.1 实际执行方式

本轮使用 4 个相互隔离的 ego-browser 任务空间：

- 主测试：登录页、性能、空值/无效账号、未登录深链、桌面和移动端布局、截图与可访问性采样。
- 律师流程：README 律师账号登录与健康接口复测。
- 助理/感官体验：1440×900、1280×720、390×844 下的视觉、键盘、密码显隐和助理登录。
- 异常/权限一致性：律师、助理、财务登录，未登录深链、刷新/返回、特殊字符、敏感信息和重复提交。

用户指定 Luna（max）作为子 agent。当前调度器实际拒绝了 `model: "luna"`，因此没有 Luna 请求被执行。三路子测试实际使用的是 `gpt-5.6-terra`、`reasoning_effort: max`；本报告不把回退模型冒充为 Luna。

## 6. 已确认问题与风险

### BR-01：后端未监听导致全部认证和业务 API 不可用

- 严重度：P0
- 置信度：确认
- 复现：打开 `/login`，使用 README 任一律师/助理/财务账号登录。
- 预期：进入对应角色工作台。
- 实际：API 500、页面停留登录页；Vite 记录 `ECONNREFUSED 127.0.0.1:8080`。
- 小律所影响：任何人员都不能开始工作，培训、试用和验收均无法进行。

### BR-02：本地数据库版本落后于当前源码

- 严重度：P0（复测与放行阻断）
- 置信度：确认的版本漂移；尚未执行兼容性破坏验证
- 实际：DB 为 v4，源码为 v13。
- 风险：直接启动当前后端可能遇到 schema 门禁失败或运行时初始化/AutoMigrate 写入。
- 本轮处理：依据安全边界，没有在未获确认时启动会写数据库的后端。

### BR-03：生产 readiness 明确不满足

- 严重度：P0（生产放行）
- 置信度：确认
- 实际：存在 11 个 active `@example.test` 演示账号；当前后端也没有提供真实 `/health/ready` 响应。
- 影响：即便本地登录恢复，也不能据此宣称可录入真实客户案件。

### BR-04：服务故障被误导为账号密码错误，并出现双重提示

- 严重度：P1
- 置信度：确认
- 实际：同一次 500 同时显示“服务器错误”和“登录失败，请检查账号和密码”。
- 来源旁证：HTTP 拦截器先显示“服务器错误”，登录页面 catch 再显示凭据错误。
- 小律所影响：使用者会反复改密码或联系管理员，延长停机恢复时间，也可能触发不必要的账号锁定流程。
- 建议：登录请求的 5xx/网络错误只显示一条可行动提示，例如“系统服务暂不可用，请稍后重试或联系管理员”；只有 401/明确凭据错误才提示账号或密码错误。

### BR-05：账号字段不校验邮箱格式

- 严重度：P2
- 置信度：确认
- 复现：输入 `not-an-email` 和虚构密码后提交。
- 实际：无字段错误，仍发起 `/api/v1/auth/login`。
- 建议：若产品只接受邮箱，应加邮箱格式校验；若还接受短账号，应把“账号或邮箱”的规则和示例写清楚。

### BR-06：登录标题对比度不足

- 严重度：P2
- 置信度：确认
- 实测：标题 `rgb(30,90,141)` 对深色卡片背景约 2.02:1。
- 影响：低视力、低亮度屏幕和会议室投屏下不易辨识。
- 建议：大字号文本至少达到 3:1；普通文本达到 4.5:1。

### BR-07：密码显隐控件键盘不可达

- 严重度：P2
- 置信度：确认
- 实测：控件为 `SPAN role=img`、`tabIndex=-1`，可访问名称仅为图标名 `eye-invisible`，无操作性中文名称/tooltip。
- 影响：键盘用户不能切换密码显隐，屏幕阅读器也难以理解当前状态。
- 建议：使用可聚焦 button，动态名称为“显示密码/隐藏密码”，同步 `aria-pressed` 或等价状态。

### BR-08：登录页缺少故障支持和首次上手路径

- 严重度：P2
- 置信度：确认的可见信息缺口
- 实际：页面仅有标题、账号、密码、记住我、登录和版权，无忘记密码、账号来源或故障联系入口。
- 建议：生产环境提供密码找回/支持入口；隔离演示环境可说明匿名账号从何处获取，但不要在页面直接展示共享密码。

### BR-09：前端健康路径可能误导运维人员

- 严重度：P2（运维可观测性）
- 置信度：确认
- 实际：前端端口 `/health*` 返回 SPA HTML 200，而 `/api/v1/health` 因后端不可达返回 500。
- 建议：运维文档与探针明确区分前端存活和后端就绪；生产流量门禁只使用后端 `/health/ready`，并校验 JSON 内容而非只看 200。

## 9. 建议修复顺序

1. P0：确定一份可恢复的 v13 非生产数据库副本，消除 v4/v13 漂移。
2. P0：启动后端并确认 `:8080` LISTEN、`/health/live` 与 `/health/ready` 语义正确。
3. P0：四角色真实登录冒烟；失败时从后端日志和响应体定位，而不是继续前端重试。
4. P1：统一登录错误所有权，避免 HTTP 层与页面层同时 toast；按 401、403、429、5xx、网络错误分别给可行动文案。

6. P2：修复标题对比度、密码显隐键盘语义、账号格式规则和支持入口。
7. 放行前：停用所有演示账号并完成真实生产 readiness 与治理证据链。
