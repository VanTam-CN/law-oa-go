# P0 利益冲突三角色真实使用演练报告

## 1. 验收信息

- 日期：2026-07-19
- 目标：站在不会 IT 的律所使用者角度，验证多用户冲突检查、独立复核、审批门禁和隔离墙是否符合真实操作习惯。
- 前端：`http://127.0.0.1:3003`
- 后端：`http://127.0.0.1:8080`
- 数据库：隔离 QA 数据库 `law_oa_db`（当前本机 development 配置）
- 数据：全部为虚构验收数据，不含真实客户、案件、身份证号、统一社会信用代码、密码或令牌。
- 环境：浏览器主流程使用隔离 QA 的 `development` 实例；另行执行了 `production` 配置 fail-closed 验证。浏览器主流程仍不能替代正式环境放行。

## 2. 演练角色与数据

| 角色 | 业务身份 | 应看到的范围 | 演练数据 |
|---|---|---|---|
| A | 承办律师 | 自己的案件、自己的冲突任务；历史命中只看受限提示 | A 角新客户合同争议（虚构） |
| B | 另一名承办律师 | 只能看到自己的案件和检测结果，不能读取 A 的受限案件 | B 角独立案件（虚构） |
| C | 独立冲突核查人 | 可查看冲突复核所需的历史命中与证据，可指定复核人、声明回避并形成结论 | A 案的名称候选高风险命中 |

场景主体使用虚构的当前对方名称、历史主体名称、曾用名和关联主体，专门覆盖名称候选、关联方、无命中、信息不足和隔离墙路径。

## 3. 操作路径与结果

### 3.1 A 律师：从工作台进入冲突复核

1. 使用 Chrome Computer Use 打开登录页并登录 A 账号。
2. 工作台显示正式 API、A 用户身份、冲突任务数量和待审批事项。
3. 点击“查看全部冲突任务”，进入 `/conflict`。
4. 页面默认是“利益冲突检测清单”，未自动弹出详情；这符合先选案件、再看结果的使用习惯。
5. A 看到自己的检测记录为“待人工复核/存在受限命中”，页面明确提示“存在受隔离记录，请联系独立冲突核查人”。
6. 点击“查看详情”：
   - 可看到当前接案上下文和待核对的当前主体名称；
   - 历史案件名称、历史案情、策略和证据被替换为受限提示；
   - 不向承办律师泄露历史客户的业务属性；
   - 页面明确说明当前不能据此确认“无冲突”。
7. A 点击“发起冲突审批”，进入 `/approval/:id`；当前审批人为 C，A 不能自审自批。

结果：**PASS**。承办律师能完成“看到任务、理解不能自行放行、转交独立复核”的完整路径。

### 3.2 A 律师：从案件详情寻找下一步

1. 打开 A 案详情 `/case/2`。
2. 案件虽然处于办理中状态，但冲突任务仍为待人工复核。
3. 页面显示“下一步操作”“下一步：利益冲突复核”和“进入本案冲突复核”。
4. 点击后跳转到带案件编号、案件标题和 `case_id` 的冲突清单上下文。
5. 点击“查看本案检测结果”可以回到该案件对应的检测详情。

结果：**PASS**。案件状态不会再掩盖冲突复核这一实际下一步。

### 3.3 C 核查人：查看、指定复核和形成结论

1. 使用 C 账号打开冲突清单。
2. C 能看到 A 案高风险名称候选的完整历史命中和证据；这与普通承办律师的受限视图不同。
3. 打开详情后，证据链显示实际证据数量，不再显示“证据链（0）”的误导性空状态。
4. 选择 C 为独立复核人并提交回避/独立性声明。
5. 选择复核结论“信息不足”，填写依据：当前名称与别名存在候选关系，但缺少唯一主体标识，不能确认是否为同一主体。
6. 提交后页面显示复核人、结论、时间、依据和证据指纹；任务仍保持阻断，不变成“无冲突”。

结果：**PASS**。信息不足不会被错误解释成无冲突，复核过程有审计留痕。

### 3.4 C 核查人：审批成案门禁

1. 打开 A 案对应审批详情。
2. 页面显示当前复核结论为信息不足，审批状态仍为“已提交”。
3. “同意并成案”按钮为 disabled，并在冲突摘要中显示：当前不能同意并成案，需要补充主体身份材料并重新复核，或退回修改。
4. 使用同一登录会话直接发送一次负向 API 请求验证后端门禁，返回：
   - HTTP `409`
   - `CONFLICT_REVIEW_INSUFFICIENT`
   - “冲突复核结论为信息不足，请补充主体身份材料并重新复核后再处理”
5. 重新读取审批记录，状态仍为 `submitted`，未创建正式案件，正式案件 ID 为空。

结果：**PASS**。前端按钮和后端状态机双重阻断；不能通过浏览器绕过前端按钮直接成案。

### 3.5 B 律师：无冲突结果与隔离边界

1. 使用 B 账号登录。
2. `/conflict` 默认清单只显示 B 的检测记录。
3. B 看到的是“提示/未发现可识别冲突/无命中”，不是“待人工复核/存在受限命中”。完整覆盖且无命中的结果被正确保留为无命中三态。
4. `/case` 只显示 B 案，不显示 A 案。
5. 直接打开 `/case/2`：后端拒绝访问；页面显示“案件不存在或当前账号无权访问”，并提示案件启用了隔离墙。

结果：**PASS**。无命中和受限命中被区分；B 无法通过列表或直接 URL 获取 A 案。

### 3.6 工作台兼容性回归

1. 使用多角色访问工作台，接口返回 200。
2. 修复前台账表缺少 `deleted_at` 时会产生 SQL 错误但接口仍返回 200 的问题。
3. 当前代码按实际列存在性构造 `inbox_items` 查询条件，最新回归请求没有再出现该 SQL 错误。

结果：**PASS**。

### 3.7 服务启动与卷宗路由回归

1. 重启后端并检查启动日志，未再出现 Gin 路由注册 panic，也未出现“恢复路由初始化 panic 后继续启动”的情况。
2. 路由表实际注册了 `GET /api/v1/cases/:id/folders`，并且该卷宗路由继承案件隔离墙中间件。
3. 以无权访问该案件的 C 会话调用该接口，返回 HTTP `403 FORBIDDEN`，而不是路由不存在的 `404`；这证明接口已注册并执行了对象授权。
4. 移除了 `router.Init` 吞掉路由注册 panic 的全局 recover。后续路由冲突会使启动失败，避免服务以缺失接口的状态运行。

结果：**PASS**。本轮发现的启动级路由阻塞已修复并完成运行态核验。

### 3.8 修复后回归与缓存边界

1. 重启后端加载最新代码，启动日志无 Gin 路由 panic；PostgreSQL、Redis 和 Elasticsearch 连接成功。
2. C 会话重新打开 `/conflict`，清单正常加载 2 条虚构检测记录，其中 1 条高风险待人工复核；页面仍明确显示“不能据此确认无冲突”。
3. C 会话访问 A 案卷宗接口 `GET /api/v1/cases/5/folders`，返回 HTTP `403 FORBIDDEN`；不带令牌的同一请求返回 HTTP `401`。
4. C 会话直接调用 A 案审批的“同意并成案”接口，仍返回 HTTP `409 CONFLICT_REVIEW_INSUFFICIENT`，审批状态和正式案件 ID 未变化。
5. 移除冲突检测原始记录和客户关系的 Redis 缓存写入。原实现以 `client_id` 作为缓存键并保存原始对象，既不能满足 P0 的隔离要求，也没有实际读取路径；修复后冲突证据只从受授权的数据库上下文读取。

结果：**PASS**。关键接口在重启后仍保持默认拒绝、复核阻断和最小披露行为。

## 5. 仍需明确的边界

1. 本次验证的是虚构数据和隔离 QA 数据库，不能证明真实律所档案已经完整导入。
2. 隔离 QA 数据库只读核对显示四个必需范围均为 `ACTIVE/COMPLETE`、索引运行已完成且缺口为 `[]`，演示账号和明文身份字段计数均为 0；这只是 QA 数据条件证据，不是律所真实档案覆盖证明。
3. `production` 配置 fail-closed 已验证：使用 `DB_SSLMODE=disable` 时应用在加载配置阶段直接退出；使用 `DB_SSLMODE=require` 连接当前无 TLS 的 QA PostgreSQL 时连接被拒绝。正式环境必须提供真实 TLS 数据库连接，当前 QA 实例不能伪装成 production readiness。
4. 本轮故意保留“信息不足”结论，未实际执行审批通过和正式成案，避免把不完整主体证据变成正式案件。
5. “无命中”只表示在已确认完整的登记范围内未发现可识别匹配，不等于法律意义上的绝对无冲突。
6. 真实上线前仍需由律所确认权威档案来源、未导入档案登记规则、独立复核人代理、豁免权限和受控对外动作清单。
7. 当前 QA 数据库的三角色账号已由 `cmd/qa-fixture` 统一创建，使用 `qa.invalid` 虚构域名；不应把历史演示账号或真实业务账号混入验收。重复执行必须通过 `QA_PASSWORD` 注入密码，并用 `-mode verify` 核验。
8. 当前仓库已补齐 canonical Kubernetes 前端 Deployment、Service、read-only Nginx 运行方式和 `/health` 探针；本轮已完成本地 ARM64 镜像和只读容器验证，但尚未验证正式集群的 Ingress、TLS、DNS 和真实前端公网入口。
9. Helm Chart 已标记为弃用并清理默认密码，CI 不再调用它；任何仍使用旧 Chart 的环境都必须先迁移到 `k8s/` 清单，否则不能纳入生产支持范围。

## 7. 结论

在虚构三角色数据下，律师 A、律师 B、独立核查人 C 的核心冲突检查路径、信息隔离、人工复核和成案阻断逻辑符合 P0 试用场景。当前“信息不足”案件已不能通过按钮或直接 API 进入正式成案。服务启动时的路由缺失风险也已改为 fail-closed，并完成运行态验证。

本报告结论为：**本轮使用固定虚构种子数据完成了 A/B/C 三角色浏览器仿真：A 的受限命中和审批阻断、C 的证据查看与“信息不足”复核、B 的本人案件访问和对 A 资源的 403 隔离均通过；审批摘要的命中主体和证据链问题也已修正并回归通过。当前代码在 QA 环境完成后端全量测试、前端门禁、ARM64 生产镜像构建和关键浏览器门禁回归，但正式生产仍不放行。上线前仍需完成 production TLS/集群部署验证、真实档案覆盖证明、AT-01 至 AT-12 全部验收和律所 PD-01 至 PD-07 七项决策物签署；本机浏览器结果不能替代正式环境证据。**
