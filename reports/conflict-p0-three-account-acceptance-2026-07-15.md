# P0 冲突检查三角色验收记录

- 日期：2026-07-15
- 验收范围：站在不会 IT 的律所使用者角度，验证普通律师、另一名普通律师、独立冲突核查人三种角色的真实操作路径。
- 环境：本机前端 `http://127.0.0.1:3003`，本机 API `http://127.0.0.1:8080`，Docker PostgreSQL。
- 方法：Chrome 页面操作、Computer Use 可见登录冒烟、浏览器端逐页操作、服务端授权与单元测试交叉验证。
- 数据：仅使用虚构演练账户、虚构客户、虚构案件和虚构历史事项；未使用真实客户资料。

## 演练角色

| 角色 | 演练账户 | 预期可见范围 |
| --- | --- | --- |
| 律师 A | `demo.lawyer@example.test` | 自己可办理的案件和冲突任务；受限历史命中只能看脱敏投影 |
| 律师 B | `demo.lawyer.b@example.test` | 自己可办理的案件和客户；不得看到律师 A 的业务属性 |
| 独立冲突核查人 | `demo.conflict.officer@example.test` | 全所冲突任务和完整复核证据；不承担普通案件列表的越权能力 |

本轮为本地验收种子账户。为修复第三角色无法登录的种子问题，新增并应用了 `000055_conflict_officer_password_repair`，该变更只修复本地虚构验收账号的密码哈希，不应作为生产账号配置使用。

## 真实使用路径与结果

### 1. 律师 A：发现命中并交给独立复核

1. 使用 Chrome 打开登录页，以律师 A 登录；Computer Use 通过可见浏览器确认登录后进入工作台，页面显示律师姓名和角色。
2. 进入“利益冲突检测清单”，查看任务列表。
3. 打开一条未完成独立复核的任务，确认页面显示“需要独立人工复核”，而不是“无冲突”或“检查通过”。
4. 查看检测范围，页面显示“系统已导入的全量历史（未导入档案需另行人工核查）”。
5. 查看命中详情，普通律师看不到受隔离历史事项的案件编号、标题、案情描述、承办团队和证据链，只能看到受限命中提示、风险类别和联系核查岗的下一步。
6. 页面明确提示当前账号只能查看，需由主任或合规/核查角色完成人工复核。

结果：通过。律师 A 能知道“存在需要处理的冲突风险”和下一步找谁，但不会因详情页面泄露历史案件业务属性。

### 2. 律师 B：验证多用户数据边界

1. 退出律师 A，使用律师 B 登录。
2. 查看工作台、冲突清单、客户列表和案件列表。
3. 工作台只显示 B 可访问的业务范围；冲突清单不出现律师 A 的专属业务标题。
4. 客户页只出现“示例隔离测试客户B”。
5. 案件页显示 B 自己可办理的两条案件，客户总数为 `1`，与客户页一致。
6. 对 `DEMO-HIGH-2026-001` 的可见性属于 B 自己拥有该案件的正常访问，不构成跨律师泄露；A-only 的业务属性未在 B 的列表和聚合数据中出现。

结果：通过，且修复了之前案件页客户总数与客户范围不一致的问题。仍需在真实律所导入数据后继续做反向越权回归。

### 3. 独立冲突核查人：查看完整证据并进行复核

1. 使用独立冲突核查人账户登录。
2. 进入冲突清单，页面显示全所冲突任务，符合冲突核查人的职责范围。
3. 打开任务“冲突检测人工验收-20260713”的检测详情。
4. 页面显示机器检测已阻断、等待独立复核、完整检测范围、规范化主体、风险分数、命中案件明细和证据链。
5. 受保护的历史事项 `DEMO-HIGH-2026-001` 在核查人视角可见，便于核查人判断是否属于同一主体、关联方或其他冲突类型。
6. 页面提供人工复核结论选择和提交入口；本轮只验证控件、权限和证据展示，不提交新的结论，避免污染验收种子数据。

结果：通过。核查人能看到普通律师不应看到的完整复核证据，并具备人工复核入口。

## 本轮发现的问题

### ISSUE-01 P1：从案件详情进入本案复核时，未自动匹配已有检测记录

复现路径：

1. 从案件详情进入案件 `DEMO-HIGH-2026-001` 的“本案冲突复核”。
2. 页面带上 `case_id=44`、案件编号和标题上下文。
3. 页面显示“暂未在冲突任务队列中匹配到本案检测记录”，要求用户确认是否从立案工作台运行过检测。

实际数据中已有一条冲突检测记录；案件命中信息位于检测结果的嵌套 `conflictCases` 中，包含 `caseId=44` 和案件编号。清单中手动打开该任务可以看到正确记录，但从案件上下文进入时未被自动选中。

影响：律师会误以为系统没有检测结果，可能重复检测或不知道下一步；这属于流程可用性和结果关联错误，不是本轮发现的越权泄露。

建议：案件上下文匹配同时覆盖检测任务关联案件字段和结果内的 `caseId/caseNo`；匹配成功后直接显示“查看本案检测结果”，匹配失败才显示“暂无记录”，并记录匹配失败原因。

### ISSUE-02 P1：成案后主体变更与对外动作门禁尚未形成可验收闭环

本轮未能用浏览器证明新增对方、变更客户、变更承办律师后会进入阻断式重检，也未证明发函、立案、出具法律意见等对外动作必须绑定已生效主体版本。该项仍是正式上线前的硬门槛，不能用人工提醒替代。

### ISSUE-03 P2：自动检索范围仍依赖已导入数据

页面已经正确提示“未导入档案需另行人工核查”，但这不等于律所已经完成权威档案库全量导入。上线前仍需由律所确认权威来源、缺口登记规则、导入范围和超范围处置方式。

### ISSUE-04 P2：本地验收种子账户曾存在密码哈希不一致

独立核查人种子账户初次登录失败，确认是种子密码哈希与其他验收账户不一致；已通过 `000055_conflict_officer_password_repair` 修复并重新验证登录。该问题属于验收环境问题，不是用户业务流程缺陷，但应保留在种子初始化检查中。

## 放行结论

当前版本可以作为**本地受控演练版本**，用于验证“机器发现风险 -> 普通律师看到脱敏结果 -> 独立核查人查看完整证据”的三角色主流程。它还不能据此作为面向真实律师的无条件生产放行版本。

正式试用前至少还应完成并重新验收：

1. 修复 ISSUE-01 的案件上下文与检测记录自动关联。
2. 交付并验证主体变更后的阻断式重检状态机。
3. 将对外动作绑定到已生效主体版本，阻断系统外影子流程。
4. 完成律所权威档案导入、关联方/曾用名/身份标识数据治理和缺口登记。
5. 用律所合规负责人确认复核、豁免、隔离墙和审计留存规则后，再进行真实业务试用。
