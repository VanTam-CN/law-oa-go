# P0 利益冲突检查多角色真实使用演练记录

**演练日期**：2026-07-16
**环境**：本地验收环境（前端 `http://127.0.0.1:3003`，后端 `http://127.0.0.1:8080`，PostgreSQL、Redis、Elasticsearch 已启动）
**依据**：`docs/利益冲突/conflict-p0-law-firm-trial-spec.md` 及 `reports/lawyer-trial-acceptance-plan-v1.md`
**演练性质**：受控本地 QA，不构成生产放行签字
**数据说明**：本次使用脱敏、虚构的本地种子数据，不使用真实客户、真实案件或真实身份标识。

## 1. 演练目标

本次不以“页面能打开”为通过标准，而是模拟一个不会 IT 的律所使用者在多用户环境中的自然工作路径，验证以下问题：

1. 新案承办律师能否从立案入口完成一次有明确风险边界的全所冲突检索。
2. 检索覆盖不足时，系统是否阻止用户把“未发现匹配”误认为“确认无冲突”。
3. 无关律师是否无法通过工作台、案件列表、冲突列表或审批详情看到其他律师的业务数据。
4. 独立冲突核查人是否能看到完成复核所需的原始证据和操作入口。
5. 助理是否只能整理草稿，不能代替律师录入身份标识、作最终冲突结论或提交审批。
6. 普通律师在审批详情中是否只看到履行工作所需的最小信息，不会看到受隔离历史案件的案号、标题、客户或证据。
7. 页面上的按钮和说明是否能让使用者知道下一步做什么，以及哪些状态仍然不能继续。

## 2. 角色和虚构业务场景

| 角色 | 使用者理解 | 本次职责 | 预期可见范围 |
|---|---|---|---|
| 律师 A | 新案承办律师 | 为虚构客户“上海示例科技有限公司”拟接一宗与“星澜科技有限公司”有关的商事争议，发起全所冲突检查 | 自己的立案、待办、脱敏后的结果和审批进度 |
| 律师 B | 与本案无关的承办律师 | 在自己的工作台处理独立案件，主动观察是否能看到 A 的任务 | 自己负责或被授权的数据；不得看到 A 的任务和案件 |
| 冲突核查人 C | 独立、非承办的专业复核人 | 查看全所冲突任务，核对原始命中证据，作人工复核决定 | 全所冲突任务及完成复核所需的原始证据 |
| 助理 | 录入和整理人员 | 协助整理案件摘要和材料清单，不作冲突结论 | 协作草稿，不得录入身份标识或执行最终检索 |

场景主线为：律师 A 创建虚构案件“QA-律师A-主体冲突复核-20260716”，填写客户、对方、案件类型和案情摘要，运行冲突检查；由于本地环境未配置律所权威档案库和关联信息源，系统应进入“范围受限，待人工复核”，而不是显示无条件通过。随后由 C 查看完整证据，A 只能看到脱敏结果，B 验证隔离，助理验证协作边界。

## 3. 使用者演练结果

### 3.1 律师 A：新建案件并运行冲突检查

| 步骤 | 实际操作 | 结果 | 判定 |
|---|---|---|---|
| A-01 | 从工作台进入“新建立案” | 打开立案工作台，按钮和步骤条可理解 | PASS |
| A-02 | 填写案件名称、案件类型、业务领域、案情摘要、客户、对方和负责律师 | 表单接受虚构数据，客户和负责律师均可选择 | PASS |
| A-03 | 点击“保存并进行利益冲突检查” | 使用正式 API 执行检查，页面显示加载过程和完成反馈 | PASS |
| A-04 | 查看检索结论 | 页面显示“已完成 · 检索范围受限，需人工复核”，并说明权威档案和关联信息源尚未配置 | PASS |
| A-05 | 尝试继续提交审批 | “提交审批并等待成案”处于不可用状态，页面没有把范围受限结果包装成“无冲突” | PASS |
| A-06 | 查看检测详情 | 能看到检索状态、覆盖边界、命中数量和后续人工复核方向；未将“检查完成”写成“冲突确认通过” | PASS |
| A-07 | 从本次检测详情进入冲突工作台 | URL 带有任务和立案上下文，页面能匹配到当前任务，不再错误显示“暂未匹配到本案检测记录” | PASS（本轮修复） |

**使用者结论**：核心流程的状态方向是正确的。一个普通律师能理解“系统已经检索过，但现在还不能据此接案”，这符合 P0 的 fail-closed 要求。正式上线前仍必须由律所配置权威来源和覆盖范围，否则只能验证“覆盖受限时阻断”，不能验证“全量检索后无冲突”的正向放行。

### 3.2 律师 A：冲突任务和审批信息的最小披露

| 步骤 | 实际操作 | 结果 | 判定 |
|---|---|---|---|
| A-08 | 在冲突详情中查看历史命中 | 历史案件显示为“受限历史事项”，并显示“存在受限命中，请联系独立冲突核查人” | PASS |
| A-09 | 查看风险和冲突类型 | 普通律师不再看到原始风险等级、结构化候选类型或历史案件业务属性，统一显示“受限” | PASS（本轮修复） |
| A-10 | 点击“发起冲突审批” | 成功创建审批记录，页面显示审批编号、状态和当前审批人 | PASS |
| A-11 | 查看审批详情 | 能看到“申请人不能审批自己的申请，仅可查看审批进度”，决策按钮不可用于自审 | PASS |
| A-12 | 检查隔离信息是否泄漏 | 服务端返回的审批元数据和冲突结果已按角色投影；未发现历史案号、标题、客户名或原始证据 | PASS（P0 修复） |

本轮修复前，A 在审批详情中可以看到隔离案件的案号、历史标题、客户和匹配证据。这是实际发现的 P0 泄密问题，已通过服务端投影和前端受限展示修复。验证结果中未出现以下敏感信息：历史案号、历史案件标题、历史客户名称、原始证据文本。

### 3.3 律师 B：无关律师的隔离验证

| 检查位置 | 实际结果 | 判定 |
|---|---|---|
| 工作台 | B 只能看到自己的待办、冲突任务和案件，不显示 A 的虚构案件标题 | PASS |
| 冲突任务清单 | B 能看到自己的任务，但不能看到 A 的任务；页面没有 A 的上下文标题 | PASS |
| 案件列表 | B 只能看到自己的两条虚构案件，A 的新案和历史事项均不在列表中 | PASS |
| 普通页面导航 | B 的侧栏不提供专业冲突核查详情入口 | PASS |
| 直接审批详情 | 本轮未通过浏览器历史导航完成直接 URL 的单独验证，不能据此签发该项放行结论 | GAP |

**使用者结论**：从常规页面入口操作时，B 不会意外看到 A 的任务或案件。P0 Spec 要求的直接 URL、聚合数据、缓存和附件下载仍需在 API/浏览器自动化验收中逐项验证，不能只凭侧栏隐藏来证明隔离完整。

### 3.4 冲突核查人 C：查看证据并进入人工复核

| 步骤 | 实际操作 | 结果 | 判定 |
|---|---|---|---|
| C-01 | 登录专业冲突核查人账号 | 角色显示为 `conflict_officer`，可见冲突检查入口 | PASS |
| C-02 | 打开冲突任务清单 | 能看到全所冲突任务，包括 A 的虚构案件 | PASS |
| C-03 | 打开 A 的检测详情 | 显示本案上下文、命中主体、历史案件及原始匹配证据 | PASS |
| C-04 | 查看人工复核区 | 显示独立复核指定、复核结论选择和提交人工复核结论入口 | PASS |
| C-05 | 提交最终复核结论 | 本轮没有提交，避免污染后续验收数据 | NOT RUN |

C 能看到完整证据是必要的权限差异，但这不意味着其他律师也应看到同样内容。当前角色边界符合“普通律师最小披露、专业核查人完整复核”的设计。

## 6. 按 P0 Spec 的放行判断

### 已有证据支持的部分

- 覆盖受限时 fail-closed：结果明确提示限制，不能提交审批。
- 冲突列表默认是清单模式，不会无上下文自动打开错误详情。
- 从当前案件进入冲突复核时，任务上下文可被正确识别。
- 普通律师与专业冲突核查人的证据可见范围已经区分。
- 审批申请人不能自审，当前审批人和审批进度在页面可见。
- 常规工作台、冲突列表、案件列表的数据隔离在 A/B 多角色演练中成立。
- 助理被限制在协作草稿，不具备最终冲突结论入口。

### 仍不能作为生产放行依据的部分

1. 律所尚未确认权威档案库、导入范围、业务范围和未导入资料的缺口登记规则；因此“全量检索”边界尚未成立。
2. 真实部署目标数据库的空库启动、迁移、备份恢复和服务就绪证据尚未在本记录中完成。
3. 成案后主体变更的强制重检必须由后端状态机和所有对外动作共同阻断，不能用人工提醒替代。
4. 直接 URL、聚合统计、附件、导出、缓存等旁路访问仍需逐项做无关律师负向验证。
5. 豁免、独立复核代理、保留期限和个人信息字段加密等七项律所决策尚未签署冻结，系统不能自行假定这些政策。

## 7. 后续最小闭环

按优先级，下一轮应使用新的脱敏数据集完成：

1. 由律所签署权威来源和覆盖范围决策，并在系统配置中形成可审计的 coverage snapshot。
2. 用无关律师 B 逐项访问 A 的案件、冲突任务、审批详情、聚合接口、附件和导出接口，保留响应状态和页面证据。
3. 由 C 完成一次“待确认/存在冲突/无冲突”中的正式复核，并验证审批、审计和隔离信息均留痕。
4. 创建主体版本变更，验证新增对方或承办律师变更会进入 `RECHECK_REQUIRED`，且发函、立案、出文、生成正式案件均被阻断。
5. 在空库和恢复场景执行部署验收，再由律所合规负责人签署放行结论。

**当前结论**：本地多角色使用演练已证明核心交互方向和本轮泄密修复有效，但项目仍是“可继续受控验收”，不是“已满足生产发布”。P0 放行仍取决于律所政策冻结、全量来源配置、旁路授权验证和主体变更状态机证据。
