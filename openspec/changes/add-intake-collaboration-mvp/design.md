# 设计索引与关键决定

完整设计维护在[接案协作 MVP 主方案](../../../docs/plans/2026-09-22-intake-collaboration-mvp-glm.md)，避免两份细节发生漂移。

## Context

主树有未提交工作；历史参考候选 a806831 含草稿/版本/审批并发修复。基线确认、隔离目录和旧修复包含检查见主方案第 2、10 节。

## Goals / Non-Goals

目标是原地新建客户、可办理待办和结构化退回重提，加上必要的草稿/手册衔接。文档中心、成案后通用任务、外部通知和生产发布后置，详见主方案第 1 节。

## Decisions

1. 客户创建复用现有服务，按操作者/操作/key 持久化幂等，不按名称自动合并主体。详见第 4 节。
2. inbox_items 增加字符串 source_ref 和完成方式；WorkflowAction 是服务端授权后的展示契约，不是授权凭据。详见第 5 节。
3. 业务转移与协作待办同事务；未办业务任务不能被普通完成/删除接口隐藏。详见第 5.3、5.4 节。
4. 退回项复用 ApprovalRecord.ImposedRequirements，回复绑定退回记录和稳定 item_id。详见第 6.1、6.2 节。
5. 复用 approval_snapshots，新快照类型 intake_submission 追加版本；当前审批使用显式 active_submission_snapshot_id，全部消费者读取同一权威来源。详见第 6.3 节。
6. 重提、唯一绑定、新快照、指派与待办交接原子提交；旧快照不覆盖，旧页面决定按轮次拒绝。详见第 6.4、6.5 节。

## Risks / Trade-offs

审批轮次与快照变化风险最高，必须先后端验证再接页面。已有数字待办来源不能猜成 UUID；历史不明记录保持明确不可直达状态。为了避免消息投递丢失，本轮站内交接采用数据库事务，不引入外部队列。详见主方案第 14 节。

## Migration Plan

全部采用加法字段/索引及必要的窄幂等表；只对新受控快照类型建立版本唯一性。迁移序号启动时按真实候选确定，禁止清理历史数据来强行通过。已有新轮次时禁止盲目降级旧程序，详见主方案第 8 节。

## Open Questions

没有需要用户预先决定的普通实现问题。N0 必须核实实际分支的快照全部读写入口、事务参与方式、历史来源类型及幂等设施；按主方案默认决定落实。只有基线不可获取、既有授权无法表达需求或出现超出范围的数据变更时，报告具体差异请求决策，不借此停止无依赖部分。
