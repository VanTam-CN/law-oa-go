# 接案协作 MVP

## Why

律师接案时新增客户需要离开表单，个人待办不能稳定直达真实业务对象，退回修改还缺少可定位的清单与新一轮审批依据。下一轮要让新客户登记、保存恢复、退回补充和审批成案形成可以连续完成的协作流程。

本提案依据 2026-09-22 手册与代码静态分析，不是已完成报告。完整行为、接口、批次和验收以[主方案](../../../docs/plans/2026-09-22-intake-collaboration-mvp-glm.md)为准。

## What Changes

- 在立案内复用客户创建表单，提供权限一致的搜索分页、幂等创建与成功回填。
- 让工作台与待办共用可授权的业务动作描述，兼容字符串业务 ID。
- 对工作流任务实行随业务转移的完成机制，禁止用标记完成或删除代替办理。
- 结构化退回要求与逐项回复，复用不可变快照表，明确当前提交版本。
- 原审批事务重提时绑定新事实、有效检测与独立复核，保持唯一审批占槽和唯一成案。
- 衔接现有服务端草稿、保存反馈，并更新同候选的手册及截图。

不增加材料中心、日常任务系统、对外通知、法律期限计算或生产发布。本轮不改变独立复核、对象权限与身份保护边界。

## Impact

- Affected specs: `core-intake-workflow`、`workflow-inbox`、`approval-system`。
- Affected code: 实际主路由的 Batch01 页面、InboxList、客户/接案/审批/待办服务、快照及成案调用方、模型与加法迁移。
- 与 `enhance-core-intake-workflow`、`add-lawyer-friendly-conflict-workflow` 和既有 UX 修复重叠的基础能力直接复用；不接管或勾选其他提案的未完成工作。
- 此仓库当前没有 CLI 可列出的正式 specs，本提案添加具体协作要求；旧 changes 仍为参考约束，不将其进度视为部署证据。
- 数据库验证限定隔离 PostgreSQL；生产迁移与正式发布不在本提案执行范围。

## Execution Boundary

当前只交付方案。用户将主方案交给 GLM 并明确要求执行后，可持续完成范围内本地实现和验证，无需每批重复确认；未指定实施前不运行迁移或改变业务代码。最终须提交新候选与 C01—C18 证据，不沿用历史候选的通过结论。
