2026-11-24，Astra 6.2 对定版 `4e4fb84` 的只读复审通过。协调者完成隔离运行复核，M3 可准入 M4。具体命令、运行数量、时间、数据库增量与散列见 [verification.json](verification.json)。

| 首次候选手改 | 在 `2d4e6d0` 的全新草稿上应用候选，再手改摘要及标题，点击保存后 PG 两列都变了，来源数为 0。定版同样操作停在人工确认，PUT 为零。 |
| 已保存草稿继续办理 | 无编辑时须同时匹配对象、版本、已知历史、完整投影和当前律师资格。独立浏览器会话重开有来源草稿，保存并退出成功，额外 PUT 为零。补齐合成分类和已登记对方的详情投影后，真实按钮按原版本确认，再按确认版本发起检测。该按钮用例使用模拟确认与检测响应。正式检测器另有 PG 测试。 |

| 创建回执重放 | 同一查询取得当前行、版本和来源历史。窗口有源表、解绑后仍有历史、源表读取失败均有 PG 断言。前端识别重放时保留旧表单，须重开才取得可写版本。隔离 v14+86 基线缺少可选 042 幂等列，该兼容路径用连接专属临时表实测。新建接案的全环境防重复另行验证。 |
| 路线 B 数据保全 | 同一干净 PG 窗口完成四场景，来源 0→3，回执 0→4，其中三条关联对应版本，最后一次人工保存解绑。新会话逐字核实人工摘要。Go 与 Python 对同一窗口的目标受保护字段、对照、客户、双方主体和材料得到相同 SHA-256。 |

复跑使用独占回环 PG 16、v14 基线、受控 86 迁移和本机 Chrome。先用 Go `-race` 覆盖冻结清单与新增项，再以不同 seed 运行额外入口和原四场景；跨语言散列核对时将原四场景的 Python `before` 文件作为 `NP_GO_SHA_MANIFEST`。真实路由使用已注册的合成账号，主角色为在职律师、草稿归本人并具有客户读取权。负责律师分配字段本身不足以证明这些资格。
