## 双入口按保存前数据核验

在一次性 PostgreSQL 16.14 上创建合成接案和主体，执行注册路由的 GET 与 PUT。以保存前 PG 中的精确数组计算预期结果。拒写时比较接案整行、主体整行、草稿版本及业务错误码；成功时比较完整目标数组、另一入口的原数组及版本变化。

| 操作 | 接案和主体两个入口的结果 |
|---|---|
| 从 `[[9007199254740993],[9007199254740992,2]]` 删首，再追加 `[9007199254740992,2,9]` | 基线返回 200，把已删除的整数写回并升版。修复后均返回 409 / INTAKE_METADATA_ARRAY_AMBIGUOUS，两行和版本与保存前相同。 |
| 删首后保留可精确回传的 `[9007199254740989,2]`，再追加 `[7,9]` | 均返回 200，与从 PG 原数组计算的结果一致。 |
| 原样回传碰撞值，或只在第一个子数组末尾追加 7 | 均返回 200，两个原始整数分别保留在原位置。 |
| 两个子数组分别追加 7 和 9，幸存子数组的原形与新前缀可区分 | 均返回 200，两项追加和原值均准确落库。 |

glm-flash 给出对照“原位置编辑”和“移除旧元素后其余元素左移”的候选。其首稿对 6 个合法保存对照均误拒，调度者据此修订共享恢复函数。在含浏览器舍入值的数组中，先在原始回传内容上核对未变前缀与左移的幸存元素。若存在两种解释，就比较按位置恢复的结果与移位后应保留的 PG 原值和新尾项；精确结果不同则整笔拒写。完整未变回传沿用原顺序。该规则处理单次删除及尾部追加；一次请求中客户端只提供最终数组。
