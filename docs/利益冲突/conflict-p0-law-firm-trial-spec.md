# 律所多用户利益冲突管理 P0 正式规格

- **版本**：1.0
- **状态**：待律所政策确认后实施
- **适用发布**：受控试用；不是“无冲突”或法律意见保证
- **负责人**：产品负责人、冲突核查负责人、技术负责人
- **依据**：律师端冲突复测记录、当前代码核验、律所一线业务评审意见

## 1. 目的与发布结论

本规格把利益冲突检查从“案件文本搜索功能”升级为可在多律师律所中受控试用的合规工作流。它的目标是：

1. 每次接案前，对**已纳入本所冲突库的全量历史资料**执行服务端盲查。
2. 将“检索完成”“未发现可识别命中”“需要人工复核”“独立复核结论”严格区分，禁止用绿色图标暗示法律上不存在冲突。
3. 保证隔离墙案件不因列表、搜索、工作台聚合、导出或冲突结果而向无关人员泄露。
4. 使主体或关键律师变更必须经过服务端重检门禁，不能由网页提示或人工纪律替代。
5. 留下不可物理删除、可追溯、可更正但不篡改原记录的审计证据。

本规格实施和验收通过前，产品只能定位为“有专人陪同的技术演示或受控测试”，不得定位为律所多用户试用系统。

本规格是产品与工程约束，不替代执业地监管规定、律所冲突政策或合规负责人作出的个案判断。

## 2. 规范用语

- **MUST**：上线前必须实现并通过验收。
- **MUST NOT**：禁止实现或禁止放行的行为。
- **SHOULD**：本 P0 建议完成；不完成必须有书面风险接受及替代控制。
- **历史库**：已被导入、核验并标记为可参与冲突查询的本所资料。未电子化或未导入资料不属于自动检索范围，必须在结果中披露。
- **受限命中**：命中隔离墙资料后，只向无权查看详情的人返回最小提示。
- **有效主体版本**：经律师确认、冲突检查与必要复核后，可被正式案件和对外动作使用的主体集合。

## 3. 范围与非范围

### 3.1 P0 范围

1. 接案前全所盲查、检索范围证据、命中分级和独立复核。
2. 律师、助理、冲突核查人、主任/管理合伙人的职责分离。
3. 隔离墙在详情、列表、搜索、工作台、导出和冲突结果的统一授权。
4. 主体、关联方、关键律师变更的强制重检与后端动作门禁。
5. 冲突、豁免、隔离墙、待办的追加式审计和保留。
6. 匿名化的三角色验收数据、API 测试和真实浏览器验收。

### 3.2 非范围

1. 自动作出法律意见、自动授予豁免或自动认定“绝对无冲突”。
2. 对未导入的纸质档案、外部工商库或第三方数据源作出已检索的虚假表示。
3. 用系统替代律所的客户知情同意、回避、信息隔离培训或外部合规咨询。
4. 自动控制律师在系统外自行撰写的 Word、邮件或线下行为；P0 只门禁系统生成、导出、审批和已接入的对外动作。

## 4. 当前基线与必须替换的行为

当前实现可复用的基础包括实体、别名、关系、案件当事人、冲突记录、复核记录和隔离墙模型。P0 不得将这些基础误表述为已完成的律所级能力。

| 当前事实 | 风险 | P0 要求 |
| --- | --- | --- |
| 历史兼容分支仍可直接查询 `cases` 和 `clients`；完整 P0 表部署后正式路径已先同步并读取全所主体索引 | 未完成索引部署或历史回填时仍可能漏掉未登记主体 | 生产 readiness 必须阻断未部署索引；正式路径以全所冲突索引为唯一检索源，覆盖历史主体、别名、关系和案件角色 |
| 请求可带 `SearchYears`，前端默认五年 | 前客户或旧项目系统性漏检 | 正式检查默认全量历史；若配置窗口，结果必须为“范围受限”，不得自动放行 |
| 名称规范化删除公司后缀，规范化一致可直接 `BLOCKED` | 把疑似同一主体误写为确认冲突 | 名称命中只能暂停并复核；身份标识强一致才可标为确认同一主体 |
| 隔离墙中间件只在能解析单案 ID 的路由生效 | 列表、聚合和前端搜索可能泄露 | 所有返回案件、主体、任务或附件元数据的查询必须在服务端按白名单过滤或脱敏 |
| 助理不能创建待确认草稿 | 不符合常见立案分工 | 新增受限的助理草稿能力，不赋予律师确认、最终检索、豁免或隔离墙权限 |
| 复核记录标注为不可变，但数据库无强制机制 | 应用或级联删除可破坏证据 | 审计与关键业务证据使用追加式记录、禁止物理删除和无级联删除外键 |

## 5. 角色、职责和访问矩阵

### 5.1 系统角色

| 角色 | 可做 | MUST NOT |
| --- | --- | --- |
| 律师 | 核对主体事实、提交正式检查、查看本人案件的最小结果、申请复核/豁免 | 审批自己相关的冲突或豁免；查看受隔离案件详情；绕过重检门禁 |
| 助理 | 创建和编辑非敏感立案草稿、上传材料、催办 | 录入或修改正式身份标识；律师确认；运行最终检查；作出结论；导出主体全集；解除隔离墙 |
| 冲突核查人 | 查看被分配任务的必要证据、作出复核结论、分派与升级 | 处理本人、本人直接管理者或本人负责案件的任务；自行解除回避 |
| 主任/管理合伙人 | 在授权范围内审批重大豁免、指定核查人、处理升级 | 默认查看所有隔离案件；替代冲突核查人的日常独立复核 |
| 系统管理员 | 管理账号与技术配置 | 使用管理员身份读取冲突详情、批准豁免或解除隔离墙，除非同时获得明确的业务角色和案件授权 |

### 5.2 小型律所最低替代规则

当没有专职冲突核查人时，系统 MUST 支持“指定独立核查人”任命记录，包含任命人、任期、代理人和回避声明。任何 `REVIEW_REQUIRED`、豁免或隔离墙解除 MUST 至少由第二名与案件无利害关系的律师书面确认。

若没有满足独立性的人员，状态 MUST 为 `INDEPENDENT_REVIEW_UNAVAILABLE`；超时或无人可审 MUST NOT 自动变为通过。系统必须要求记录外部核查、相关客户书面同意或拒绝接案的处置。

### 5.3 复核人资格校验

服务端在分派和决策时 MUST 校验：

1. 复核人不是申请人、案件负责人、拟加入团队成员或其直接管理者。
2. 复核人不在受影响隔离墙的受限团队中；如因职责必须访问，必须有单独授权和访问理由。
3. 复核人账号启用、角色有效，且未处于回避、离职或请假不可用状态。
4. 不满足时返回 `409 REVIEWER_CONFLICTED`，不得只依赖前端隐藏按钮。

## 6. 主体、身份与关系数据契约

### 6.1 受检主体类型

每个主体 MUST 使用以下类型之一，并记录其在本次案件中的角色：

- `LEGAL_PERSON`：法人；正式强标识为统一社会信用代码。
- `BRANCH`：分支机构；必须关联总公司实体，不能当作独立法人误判。
- `INDIVIDUAL`：自然人；正式强标识为经核验的身份证件或护照标识。
- `ORGANIZATION`：非法人组织。
- `LAW_FIRM_SELF_INTEREST`：律所、律师本人或近亲属利益；必须走独立规则，不能混入客户名称匹配。

案件角色至少包括委托人、对方当事人、共同当事人、第三人、关联方、共同代理人、协办律所、仲裁人/法官、拟加入律师。

### 6.2 身份字段与隐私

1. 身份标识原文 MUST 加密保存；检索使用经版本化、带密钥的确定性摘要，不以明文身份证件号建索引。
2. 默认响应 MUST 返回掩码值；完整值仅向有明确业务授权的核查人展示，并记审计日志。
3. 助理不得录入或修改正式身份标识。缺少强标识时，律师必须补充或明确标记为信息不足。
4. 名称、别名、曾用名、历史统一社会信用代码、关系来源、关系有效期与可信度 MUST 可追溯。
5. 现有明文 `identity_number` 数据的迁移 MUST 先盘点、加密回填、验证摘要检索一致性，再限制旧字段读取；不得静默删除历史数据。
6. 初次接案的委托客户、对方及相关方 MUST 在律师确认事实前登记与主体类型匹配的强身份标识。客户端草稿 MUST NOT 持久化身份原文；普通接案响应 MUST NOT 返回原文、密文或摘要。
7. 客户、对方或相关方任一缺少可解密身份标识时，正式检索 MUST 返回明确的“信息不足”并阻断，不得退化为仅名称检索后形成可接案结论。
8. 客户身份 MUST 使用通用的 `identity_type`、身份密文和检索摘要表示。企业统一社会信用代码不得以 `ID_CARD` 类型进入主体索引、检索证据或审计快照；旧 `id_card_*` 字段只允许作为迁移兼容源。

### 6.3 主体匹配分级

| 证据 | 机器分类 | 工作流动作 | 对律师显示 |
| --- | --- | --- | --- |
| 经核验的强标识一致 | `IDENTITY_CONFIRMED` | 暂停接案并进入独立复核 | “发现需复核的主体一致命中” |
| 名称、别名、曾用名或规范化名称一致 | `NAME_CANDIDATE` | 暂停接案并复核 | “发现名称关联命中，待核查” |
| 自然人仅姓名相同 | `IDENTITY_INSUFFICIENT` | 要求补充身份信息，不得称为冲突 | “信息不足，需补充身份标识” |
| 母子公司、实控人、关联方 | `RELATION_CANDIDATE` | 单独评估，不得当作同一主体 | “发现关联方线索，待核查” |
| 律所自身、律师本人或近亲属 | `SELF_INTEREST_CANDIDATE` | 单独回避工作流 | “发现律所/人员利益线索，待核查” |

`IDENTITY_CONFIRMED` 仅表示主体身份强一致，不自动等于法律上已确认不可代理。最终处置只能由独立复核结论产生。

## 7. 全所盲查与检索证据

### 7.1 检索边界

1. 正式冲突检查 MUST 在服务端检索全所冲突索引，不能按发起律师、团队或案件可见性缩小检索集合。
2. 索引 MUST 覆盖已入库的现客户、前客户、准客户、案件当事人、案件角色、别名/曾用名、实体关系和历史案件主体。
3. `SearchYears <= 0` 表示全量历史。正式检查不得由前端默认五年。若律所配置了有限窗口，响应 MUST 标记 `COVERAGE_LIMITED`，禁用自动放行并创建人工复核待办。
4. 检索结果 MUST 固化：数据源版本、检索开始/结束时间、查询主体版本、检索字段、关系深度、覆盖/未覆盖来源、命中数和无命中声明。
5. 未纳入电子库、外部工商库不可用或关系资料不完整时，结果 MUST 显示保留说明；MUST NOT 显示“无冲突”或“检查通过”。
6. `has_conflict` 只表示存在实际匹配记录或确定阻断命中，不得因 `COVERAGE_LIMITED` 单独置为 `true`。覆盖受限但无证据时，页面 MUST 同时显示“未发现匹配记录”和“检索范围受限，需人工复核”；继续接案仍由 `decision.status` 与 `coverageStatus` 阻断。

### 7.2 最小披露

普通律师面对受限命中时只可看到：`存在 N 条受隔离记录，请联系冲突核查岗`。不得看到案件名称、案件号、客户行业、承办团队、案情、文件、策略或历史律师姓名。

冲突核查人、获授权的主任和被涉及历史客户的现任承办律师，只能在满足案件授权和访问目的的情况下看到最小必要详情。新案承办律师可按授权看到冲突涉及的客户身份和冲突类型，但不得看到受隔离历史案件的案情摘要、策略或工作底稿。

### 7.3 显示文案

页面 MUST 使用以下区分：

- `检索完成，未发现可识别匹配记录`：仅在覆盖完整且无命中时使用，并展示检索范围。
- `检索范围受限，需人工复核`：数据源、时间范围或关联资料不完整时使用。
- `发现需独立复核的命中`：强标识、名称或关系线索命中时使用。
- `复核结论：可继续 / 不予接案 / 已按条件豁免`：仅在独立复核产生有效结论后使用。

MUST NOT 使用“无冲突”“冲突检查通过”“名称不一致，可继续”等脱离检索范围的绝对性文案。

## 8. 接案与复核状态机

### 8.1 接案状态

```text
DRAFT
  -> LAWYER_FACTS_CONFIRMED
  -> CHECK_QUEUED
  -> CHECK_RUNNING
  -> CHECK_COMPLETED_NO_IDENTIFIABLE_MATCH
  -> REVIEW_REQUIRED
  -> INSUFFICIENT_INFORMATION
  -> WAIVER_PENDING
  -> WAIVED
  -> DECLINED
  -> APPROVED_FOR_CASE
```

规则：

1. 只有律师可从 `DRAFT` 转到 `LAWYER_FACTS_CONFIRMED`。
2. `CHECK_COMPLETED_NO_IDENTIFIABLE_MATCH` 不是法律结论；它只允许进入立案审批，前提是 `coverage_status=COMPLETE`。
3. `REVIEW_REQUIRED`、`INSUFFICIENT_INFORMATION`、`WAIVER_PENDING`、`INDEPENDENT_REVIEW_UNAVAILABLE` MUST 阻断立案审批和成案。
4. `WAIVED` 仅在有效期、条件和监督要求均有效时允许继续。
5. 复核、豁免和审批创建 MUST 幂等；同一检查和同一处置类型在有效期内只能有一条进行中或有效记录。

### 8.2 成案后主体变更状态机

对有效案件，所有实质变更先生成 `pending_subject_revision`，不得直接覆盖有效主体版本：

```text
EFFECTIVE_REVISION
  -> CHANGE_PROPOSED
  -> RECHECK_REQUIRED
  -> RECHECK_RUNNING
  -> CHANGE_APPROVED_AND_EFFECTIVE
  -> CHANGE_REJECTED
```

以下变更 MUST 触发阻断式重检：

1. 新增或变更对方当事人、共同被告、第三人、关联方。
2. 更换委托人，或合并、拆分客户主体档案。
3. 新增共同代理人、协办律所、承办律师或协办律师。
4. 身份标识实质更正，或名称/别名/历史主体关系的实质更正。

纯联系方式、内部工作记录、进度或不涉及身份识别的显示名排版调整可只记录，不强制重检。新增联系人是否触发重检由其是否成为案件主体决定。

在 `RECHECK_REQUIRED` 至 `CHANGE_APPROVED_AND_EFFECTIVE` 期间，系统 MUST 阻断与待生效主体相关的对外发函、立案、文件生成、审批和导出；原有效主体范围内的已批准工作可继续。所有已接入对外动作必须在服务端校验有效主体版本，不能只在前端禁用按钮。

#### 8.2.1 全新主体首次登记

真实案件新增的对方、第三人或其他受检主体可能尚未存在于律所主体库。该场景 MUST 复用案件主体修订作为唯一状态机，不得要求律师改用自由文本完成重检，也不得另建一个与案件主体版本脱节的临时审批结论。

1. 律师在案件内提交候选主体时，MUST 提供名称、主体类型、身份标识类型、身份标识值、案件角色和变更原因；自然人姓名相同但缺少证件标识时只能记为 `INSUFFICIENT_INFORMATION`，不得进入“确认同一主体”或“无冲突”结论。
2. 候选主体名称、曾用名和身份标识属于冲突核查资料。身份标识 MUST 使用专用密钥加密并保存带密钥摘要；API、日志和审计元数据不得返回明文。
3. 提交成功后修订进入 `ENTITY_REGISTRATION_PENDING`，案件立即保持 `RECHECK_REQUIRED`，所有受控动作继续阻断；登记确认本身不得被当作冲突复核完成。
4. 申请律师、案件负责人和直接利害关系人不得确认自己的主体登记。仅独立冲突核查人或经书面授权的业务管理人员可选择：`CREATE_NEW`、`LINK_EXISTING`、`REJECT`。
5. `CREATE_NEW` 前 MUST 按身份标识摘要全所去重；发现相同标识时不得重复创建，应由核查岗使用 `LINK_EXISTING`。普通律师不得因重复校验获知受隔离主体是否存在、名称、案件或团队。
6. `LINK_EXISTING` MUST 校验候选身份摘要与目标主体一致；不一致时失败关闭，不允许仅凭名称强行合并。合并决定和依据写入追加式审计记录。
7. `CREATE_NEW` 或 `LINK_EXISTING` 完成后，修订载荷 MUST 原子替换为正式 `entity_id` 引用，再进入 `RECHECK_REQUIRED`；随后必须以该正式主体运行冲突重检并由另一名合格复核人形成专业结论。
8. `REJECT` MUST 恢复原有效主体版本、清除待处理修订并保留申请、驳回人、时间和理由；候选主体不得进入正式主体库。
9. 搜索已有主体只可返回当前案件或当前账号获授权案件中的主体。未返回某名称不等于全所无记录，界面必须明确提示该限制。

## 9. 隔离墙与对象级授权

### 9.1 统一执行点

以下所有接口和异步查询 MUST 使用同一服务端对象授权策略：案件详情、案件列表、全文/全局搜索、工作台聚合、冲突任务列表与结果、审批摘要、导出、附件元数据、下载与打印。

隔离墙案件对非白名单用户必须满足：

1. 不出现在列表、统计、搜索候选、自动补全或工作台聚合中。
2. 不能通过直接对象 ID、任务 ID、审批 ID、导出链接或浏览器缓存重新取得元数据。
3. 冲突盲查仍可在服务端使用该记录，但返回受限计数，不返回业务属性。
4. 拒绝、允许、授权变更与读取敏感详情都必须记录审计事件。

### 9.2 防泄露实现规则

1. 禁止先把全量 `case_rows`、风险队列或审批队列发送到浏览器再在前端过滤搜索。
2. 数据库列表查询必须在 SQL/仓储层纳入伦理墙白名单条件；不能依赖详情路由中间件。
3. 管理员不因技术角色自动越过隔离墙；业务授权与系统管理员权限分离。
4. 缓存键、导出任务、日志和错误响应不得包含未授权对象的名称、编号或存在性。

## 10. 审计、更正与保留

### 10.1 追加式记录

下列事件 MUST 写入追加式审计账本：检索、无命中、命中、复核、豁免、回避、隔离墙设置/解除、授权、访问允许/拒绝、主体变更、重检、导出、归档和更正。

每条记录至少包含：事件 ID、时间、操作者、操作者角色、对象类型/ID、请求关联 ID、前后状态、主体版本、检索范围、证据摘要哈希、理由、来源和完整性哈希。敏感原文不应复制进一般审计日志。

### 10.2 不可删除与更正

1. 冲突、复核、豁免、隔离墙和审计记录 MUST NOT 提供物理删除接口。
2. 待办 MUST 改为完成、归档、撤销或移交；不得物理删除与合规流程关联的待办。
3. 更正 MUST 新增一条更正事件，引用原记录、说明理由、写入更正人和时间；原记录保留并标识已被更正。
4. 关键审计表 MUST 禁止应用数据库账号执行 `UPDATE`/`DELETE`；相关外键 MUST NOT 使用 `ON DELETE CASCADE`。
5. 保留期必须由律所政策配置，并不得低于适用的档案与合规要求。系统只负责执行配置、冻结到期策略和保留处置审计，不自行宣称法定期限。

## 11. 目标数据与 API 契约

### 11.1 数据迁移包

实现应在现有 P0 迁移链上提供以下可移植数据契约。当前仓库以 `000051` 至 `000065` 承载早期复核、范围、重检和隔离证据，`000066_conflict_p0_subject_index` 补齐主体版本、保护标识和规范化命中证据表，`000067_conflict_index_build_runs` 补齐历史索引构建与对账运行证据，`000068_conflict_policy_and_source_quality` 补齐律所政策版本和来源质量门禁，`000069_case_subject_revision_state_guard` 保护主体变更状态迁移，`000070_case_intake_party_identity` 保护初次接案主体身份，`000071_client_generic_identity` 明确客户强身份类型并迁移旧保护数据，`000072_client_creator_access` 和 `000073_client_optional_email_null` 补齐首案前客户归属及可选邮箱，`000074_approval_audit_timestamps_timezone` 固化审批审计时间的绝对时刻，`000075_client_primary_contacts` 分离并保护客户主联系人，`000076_conflict_policy_endorsement_workflow` 固化不可修改的政策材料包和管理/合规分责确认，`000077_conflict_officer_appointments` 固化冲突核查人、代理人、任命人分离及有效任期；不得把旧迁移编号或旧表中的 JSON 快照当作这些结构化契约的替代：

1. `conflict_subject_versions`：主体有效版本、确认人、确认时间、来源与版本号。
2. `conflict_subject_identifiers`：加密身份值、检索摘要、核验状态和掩码展示值。
3. `conflict_search_scopes`：每次检索的数据源、范围、字段、时间窗口、缺口与完整性状态。
4. `conflict_match_evidence_v2`：命中类型、来源、受限标记、证据快照和哈希。
5. `conflict_index_build_runs`：按案件、客户、主体、关系来源记录构建状态、源记录数、索引记录数、缺口数、对账哈希和凭证引用。
6. `conflict_reviewer_assignments`：分派、资格检查、回避、代理、SLA 与升级记录。
7. `case_subject_revisions` 与明细：待生效变更、检查关联和生效结论。
8. `compliance_audit_events`：不可删除的追加式账本。
9. `case_intake_parties`：初次接案的主体类型、身份类型、身份密文、检索摘要和别名；普通响应只暴露登记状态。
10. `clients.identity_*`：客户主档强身份的类型、密文和检索摘要；企业与自然人不得共用错误的身份类型标签。

所有新表必须兼容 MySQL 8 与 PostgreSQL，不使用数据库专有 `ENUM`、非必要触发器或级联删除。既有检查记录须标记为 `LEGACY_SCOPE_UNKNOWN`、`LEGACY_EVIDENCE_PARTIAL` 或可验证状态；历史记录不得被静默改写为 `COMPLETE`。

### 11.2 目标接口

具体路径可随现有路由命名调整，但以下服务端契约不可省略：

| 能力 | 请求 | 成功结果 | 必须拒绝 |
| --- | --- | --- | --- |
| 律师确认主体 | `POST /case-intakes/:id/facts-confirmation` | 固化主体版本 | 助理、未完整主体、版本已过期 |
| 发起正式检查 | `POST /conflict/tasks` | 返回任务和范围版本 | 非律师确认、受限覆盖被要求自动放行 |
| 查看检查结果 | `GET /conflict/tasks/:id/result` | 按角色脱敏的结果 | 非对象授权、已失效任务 |
| 提交复核 | `POST /conflict/tasks/:id/review` | 新的不可变结论 | 自审、无资格、证据版本不一致 |
| 提交主体变更 | `POST /cases/:id/subject-revisions` | `RECHECK_REQUIRED` 修订 | 绕过有效版本直接更新 |
| 执行受控动作 | 任意成案/导出/对外接口 | 校验有效主体版本 | 待重检、复核中、已拒绝或豁免失效 |
| 查询案件与搜索 | 列表/搜索/聚合接口 | 仅返回已授权对象 | 隔离墙对象泄露或存在性枚举 |

接口错误码至少区分：`403 OBJECT_FORBIDDEN`、`409 RECHECK_REQUIRED`、`409 REVIEWER_CONFLICTED`、`409 COVERAGE_LIMITED`、`409 INSUFFICIENT_INFORMATION`、`409 ACTIVE_DISPOSITION_EXISTS`。响应不得泄露隔离案件名称或编号。

## 12. 前端工作流与可访问性要求

1. 冲突结果页面必须单一来源渲染状态、文案、按钮和服务端门禁，不得出现已豁免和不得继续两套相反指令。
2. 每个状态都显示当前主体版本、检索时间、覆盖范围、缺口与下一责任人。
3. `REVIEW_REQUIRED` 显示“进入本案冲突复核”，携带任务上下文；同一视图中主操作名称唯一。
4. `CLEAR` 类展示必须使用“未发现可识别匹配记录”，并附范围说明；不使用绿色对勾暗示法律安全结论。
5. 助理视图只能看到草稿录入、资料上传和律师催办；敏感身份、复核、豁免、隔离墙和导出操作不可见且 API 不可调用。
6. 隔离墙无权限时列表中不显示记录；直接访问返回统一无权错误，不能区别“对象存在但无权”和“不存在”。

## 13. 实施工作包与依赖

### WP-01：政策与角色基础

- 新增 `conflict_officer`、`intake_assistant` 业务角色和任命/代理模型。
- 实现复核人独立性校验、回避声明和超时升级。
- 依赖：律所指定核查负责人、直接管理关系来源。
- 验收：申请人、负责人、直接管理者均无法审批；无独立复核人时保持阻断。

### WP-02：主体版本与敏感身份

- 扩展实体、别名、曾用名、关系与身份标识的版本化数据模型。
- 加密、摘要检索、掩码和历史数据迁移。
- 验收：同一强标识稳定命中；自然人同名不当作冲突；未授权响应和日志不含原始身份值。

### WP-03：全所冲突索引与证据

- 使用全所主体索引替换直接文本 SQL 主路径；纳入历史客户、案件角色、别名和关系。
- 提供默认只读的 `go run ./cmd/backfill-conflict-index`，只有显式 `--apply --evidence-reference ...` 才能写入索引；每次回填必须生成四类来源的 `COMPLETED` 对账运行记录。
- `conflict_search_scopes` 标记 `COMPLETE` 时 MUST 绑定对应 `index_run_id`，运行记录必须同源版本、零缺口、记录数闭合、哈希和凭证一致；readiness 必须复核该绑定，不能只信任人工填写的 scope 字段。
- 写入范围快照和无命中声明；实现受限命中最小披露。
- 验收：全量历史样本、未附案件的主体、别名/曾用名、关联关系和十年以上历史样本可命中；坏引用阻断回填；有限范围不能自动放行；受隔离命中不泄露属性。

### WP-04：隔离墙统一授权

- 在仓储、服务和聚合接口执行对象级过滤；移除前端全量数据搜索。
- 覆盖列表、全局搜索、工作台、冲突、审批、附件、导出和缓存。
- 验收：B 律师不能列表、搜索、直接访问、导出或从浏览器缓存获取 A 律师隔离案件信息。

### WP-05：接案与主体变更门禁

- 实现主体版本、服务端状态机、幂等处置和受控动作验证。
- 现有旧检查结果迁移为需重检或明确历史范围。
- 验收：任意 API 或并发请求均不能绕过 `RECHECK_REQUIRED`；旧主体的已批准工作与新增主体动作边界正确。

### WP-06：追加式审计与待办留存

- 新建合规审计账本，移除关键流程的物理删除与级联删除。
- 待办改为归档/完成/移交；实现更正链。
- 验收：数据库应用账号不能删改关键审计；更正保留原记录与因果链。

### WP-07：前端与文案收敛

- 统一处置状态展示、范围说明、复核入口和角色视图。
- 实现助理草稿流程和律师确认界面。
- 验收：每一状态只有一组下一步动作；屏幕阅读器按钮名称唯一；无绝对性“无冲突”表述。

### WP-08：匿名种子与三角色验收

- 建立隔离的 QA 数据库和匿名种子，不在生产库写入演练数据。
- 见第 14 节的浏览器、API、数据库验收。
- 验收：全部 MUST 场景通过，任何泄露或绕过均为阻塞缺陷。

WP-01、WP-02 是 WP-03 的前置；WP-03、WP-04、WP-05、WP-06 必须在 WP-08 之前完成。WP-07 可与后端工作并行，但不得先于服务端门禁宣称完成。

## 14. 验收数据与必须通过的场景

所有数据为虚构、匿名且只存在于隔离 QA 库。至少准备律师 A、无关律师 B、冲突核查人 C、助理 D、主任 E，以及以下资料：

1. 十年以上的前客户“远景重工”，包含别名和已终止案件。
2. A 的隔离墙案件“北辰资本收购项目”，B 未在白名单，C 按职责授权。
3. 强标识一致的法人、仅名称相似的法人、自然人同名但证件不同、集团关联和分支机构样本。
4. 已批准主体版本的案件，以及新增对方、变更委托人、新增协办律师的待生效修订样本。
5. 已回避、已分派、已超时和已豁免的复核/豁免样本。

| 编号 | 操作 | 通过条件 |
| --- | --- | --- |
| AT-01 | A 对十年以上前客户相关对方发起检查 | 历史主体命中；范围记录为全量；不因五年截断漏检 |
| AT-02 | A 命中 B 的隔离墙案件 | A 只见受限计数和联系提示；C 可在授权范围查看证据 |
| AT-03 | B 列表、搜索、工作台、直接 URL、导出、缓存检查 A 隔离案件 | 均无案件元数据，且拒绝记录留审计 |
| AT-04 | 相同信用代码与同名不同代码分别检查 | 前者暂停复核，后者不被错误认定同一主体 |
| AT-05 | 两名同名自然人、证件不同 | 状态为信息不足或非同一主体，不生成确认冲突 |
| AT-06 | 集团母子公司与分支机构样本检查 | 关联关系与同一主体分类正确、依据可见 |
| AT-07 | D 创建草稿并尝试确认、提交检查、写身份、导出 | 仅草稿权限成功，其余均由服务端拒绝 |
| AT-08 | A、负责人及直接管理者尝试审批同一任务 | 全部返回 `REVIEWER_CONFLICTED`；C 可在资格满足时审批 |
| AT-09 | 无独立复核人或 SLA 到期 | 仍阻断接案，创建升级记录，不自动通过 |
| AT-10 | 已成案后新增对方或协办律师，再直接调用导出/成案接口 | 产生待生效修订；相关动作被 `RECHECK_REQUIRED` 拒绝 |
| AT-11 | 更正、归档、删除和数据库直接删除尝试 | 仅追加更正/归档成功；关键证据无法物理删除 |
| AT-12 | 覆盖受限或关系资料不完整时检查 | 无绿色放行；显示范围受限并创建人工复核待办 |

验收必须包含 Go 单元测试、PostgreSQL 集成测试、API 越权/并发测试、Playwright 三角色 E2E，以及 Chrome 实机复核。当前生产入口仅支持 PostgreSQL；若律所仍保有 MySQL 历史实例，应先在隔离副本完成其迁移/导出一致性验证，不能将其作为本 MVP 生产安装路径。浏览器“流程可点击”不能替代 API 和数据库级验证。

## 15. 发布、迁移与回滚

1. 先以 `conflict_p0_v2` 特性开关在隔离 QA 环境运行；旧流程仅供比对，不可作为放行依据。
2. 上线前执行历史资料覆盖盘点。未入库历史必须登记数据源、责任人、预计完成日和范围缺口。
3. 迁移先新增表和双写，再校验摘要命中、审计链和权限过滤；确认后切换读路径。不得删除旧记录或静默转换旧结论。
4. 发现错误时仅回退读路径/特性开关；已产生的审计、主体版本和复核记录保留。禁止以数据库回滚删除业务证据。
5. 仅在第 14 节全部通过、范围缺口被律所书面接受且 P0 安全测试无阻塞缺陷后，才可扩大到受控试用。

## 16. 待律所确认的政策决策登记表

以下事项不是工程师或模型可以替代决定的事项。每项必须有书面决策物、版本、批准人和生效日期。未确认前，系统按更保守的阻断行为执行。

| 编号 | 需律所明确的问题 | 必须产出的决策物 | 未确认时的阻塞面 |
| --- | --- | --- | --- |

### 16.1 推荐确认顺序

1. 先冻结 PD-01 和 PD-07，确定数据范围与生命周期。
2. 再冻结 PD-05，确定身份字段、真实数据禁限和加密方案。
3. PD-03 与 PD-06 可并行确认，随后冻结系统角色、独立性校验和豁免流。
4. PD-02 与 PD-04 可并行确认，但必须分别在 WP-03/WP-05 开发前冻结；它们决定受限范围的处置和状态机接入点。

工程不得因某一项尚未完成就自行假设默认值。任何临时例外必须在审计账本记录批准人、理由、适用对象、范围、开始时间、到期时间和撤销条件。

### 16.2 种子数据与真实演练前置规则

1. 演练数据 MUST 脱敏或完全虚构；禁止使用真实客户、真实案件或真实身份标识。测试库、测试账号和生产库必须隔离。
2. 种子按第 14 节的验收场景预埋，而非只追求数据库干净。它必须覆盖精确命中、疑似命中、自然人同名、关联关系、隔离墙、成案后变更、回避和豁免。
3. PD-01 至 PD-07 若修改主体字段、覆盖范围、保留期或受控动作，必须先更新本 Spec 的版本和验收数据，再创建或重置种子。
4. 真实演练 MUST 包含反向越权验证：无关律师 B 主动尝试列表、搜索、直接 URL、导出、浏览器缓存和冲突结果访问受隔离案件 X。
5. 先由测试账号完成全流程与反向验证，再由真实合规人员验收。真实人员不得在未隔离的演练库中以真实资料试错。
