## 一、核心结论

### 1.1 产品定位诊断

> **Law OA Go v2.3.0 是一个优秀的"后端工程作品"，但目前还不是一个及格的"法律业务产品"。**
>
> 系统架构非常稳健（Go + ES + 审批流），但在业务逻辑上存在严重的"空心化"现象。
> 现在的系统是一个"存放资料的柜子"，要变成"自动运转的流水线"。

### 1.2 最致命的3个缺失

| 排名 | 缺失 | 影响 | 原因 |
|------|------|------|------|
| 1 | **移动端完全缺位** | 律师50%时间在法院/出差，没有移动端等于断了一根腿 | 无法实时审批、查冲突、看日程 |
| 2 | **文档管理仅65%** | 律师工作本质就是生产文档，当前只是网盘 | 无版本控制、无在线编辑、无卷宗目录 |
| 3 | **外部数据集成为零** | 手动录入工商信息低效且高风险 | 无法自动穿透关联关系，冲突检测不完整 |

### 1.3 竞争优势确认

**私有化部署 = 数据自主可控**，这是SaaS竞品（Alpha/法大大）无法复制的壁垒。
但私有化优势能"保命"不能"赢"，功能差距过大会导致律师私下用微信传数据，安全性优势在操作层面崩塌。

## 三、三个月 Sprint 迭代计划

### Sprint 1: 基础能力增强 (Week 1-4)

**目标**: 消除"半成品感"，建立业务红线防护

#### Week 1: 案件全生命周期 + 审批增强
- **案件阶段状态机**: 实现 线索→风控→签约→办案→庭审→结案→归档 7阶段
- **诉讼时效引擎**: 输入判决书日期自动计算上诉期(15天)、执行时效(2年)，T-7/T-3/T-0三级预警
- **审批评论与附件**: 审批单内支持讨论和补充材料
- **代理审批**: 主任出差时可委托他人代批

#### Week 2: 冲突检测 V2.1 + 审批条件分支
- **关联关系递归穿透**: PostgreSQL Recursive CTE实现3层穿透（母公司→子公司→孙公司）
- **动态冲突监测**: 案件新增/变更当事人时自动触发二次检查（事件驱动Hook）
- **审批条件分支**: 基于JSON规则引擎，支持标的额/案件类型/风险等级路由
- **审批业务联动**: 审批通过后自动触发后续操作（如立案审批通过→自动生成案号）

#### Week 3: 文档管理增强
- **ONLYOFFICE集成**: Docker部署 + Go回调接口 + 浏览器内编辑Docx
- **文档版本控制**: 覆盖上传生成新版本，支持版本锁定和回滚
- **卷宗目录模版**: 预设诉讼/非诉标准目录（程序文书/证据材料/法律文书/裁判文书/办案记录）

#### Week 4: 集成测试 + 技术债务清理
- 端到端测试：案件从创建到归档的完整流程
- 冲突检测性能测试（递归3层查询 < 5秒）
- ONLYOFFICE编辑稳定性验证
- 权限模型优化（为Sprint 2财务数据隔离打底）

**验收标准**:
- [ ] 案件能走完7个阶段完整生命周期
- [ ] 诉讼时效预警在T-7/T-3/T-0准确触发
- [ ] 冲突检测能穿透3层关联关系并输出报告
- [ ] 文档在线编辑不丢失内容，版本自动记录
- [ ] 审批支持评论、附件、条件分支

---

### Sprint 2: 核心业务闭环 (Week 5-8)

**目标**: 让律师愿意把手机掏出来

#### Week 5: 企业微信集成基座
- **企微自建应用配置**: AgentId + Secret，OAuth2免登
- **消息推送服务**: 审批待办、开庭提醒推送到企微工作台
- **移动端脚手架**: React + antd-mobile 微应用，复用API Service层
- **Go SDK集成**: 使用 `github.com/silenceper/wechat/v2`

#### Week 6: 移动端核心功能
- **移动端审批**: 消息卡片直接点通过/驳回
- **冲突审查(移动版)**: 极简表单，输入客户名一键返回红/绿灯
- **案件/文档搜索**: 基于ES的全局搜索 + PDF预览
- **我的日程**: 未来7天开庭与会议列表

#### Week 7: 财务基础模块
- **计时收费**: 网页端/移动端计时器，工时单录入（日期、时长、描述、费率）
- **费率表**: 不同律师（合伙人/授薪/助理）不同单价
- **工时审核流**: 合伙人审核工时，通过后锁定
- **回款登记**: 银行流水手动认领，关联案件/合同/发票

#### Week 8: 财务报表 + 可视化时间线
- **核心三表**: 创收贡献表、应收账龄表(AR Aging)、律师提成明细表
- **案件可视化时间轴**: 关键法律节点 + 动态操作流，颜色编码
- **合伙人分成计算器**: 固定比例模型（创收-成本-公费）自动计算
- **案件利润分析**: 固定收费案件的工时成本 vs 收费对比

**验收标准**:
- [ ] 律师在企微收到审批提醒后30秒内完成审批
- [ ] 手机端计时器可正常开始/暂停/提交
- [ ] 财务能导出准确的应收账龄表
- [ ] 合伙人能看到每个案件的利润分析
- [ ] 案件时间线展示完整的操作历史

---

### Sprint 3: 差异化与商业化 (Week 9-12)

**目标**: 塑造"专业律所管家"形象，完成付费转化

#### Week 9: 天眼查集成 + 安全加固
- **天眼查API集成**: 输入公司名自动填充工商信息（信用代码、法人、股东、投资）
- **冲突数据自动补充**: 创建Entity时可选天眼查同步关联关系
- **PII数据加密**: 身份证、手机号AES-GCM加密存储
- **数据脱敏**: 非授权用户看到掩码数据（138****1234），点击"查看明文"记录审计

#### Week 10: 知识库 + 安全增强
- **文档模板库**: 全所共享合同/诉状模板，标签分类
- **知识库自动归档**: 结案归档时自动同步文书至知识中心（脱敏处理）
- **动态水印**: 文档预览时平铺"用户名+IP+时间"半透明水印
- **细粒度审计日志**: 记录所有查看/下载/导出操作（5W1H原则）

#### Week 11: 电子签章 + 简单OCR
- **电子签章集成**: 对接e签宝/法大大API，委托协议远程签署
- **简单OCR**: 上传证据图片自动文字提取，方便搜索
- **审批超时催办**: 超过24小时未处理自动发企微/短信提醒

#### Week 12: MVP打磨 + 自动化部署
- **可视化驾驶舱**: 律所经营概览（创收、结案率、律师负载、回款率）
- **Docker一键部署优化**: 简化安装流程，减少实施成本
- **用户引导流程**: 新用户5分钟上手向导
- **全面Bug修复 + 性能优化**

**验收标准**:
- [ ] 天眼查接口自动创建Entity耗时 < 3秒
- [ ] 系统通过中等规模律所安全合规检查
- [ ] 结案文书自动进入知识库可搜索
- [ ] 电子签章可完成一次完整的签署流程
- [ ] Docker一键部署全流程 < 30分钟

## 四、YAGNI 原则：坚决不做

| 功能 | 理由 |
|------|------|
| 复杂LLM私有化部署 | 1-2人团队撑不起GPU维护，仅做API调用 |
| 完善的HRM系统 | 律所人事复杂，先用Excel导入代替 |
| 财务全科目凭证 | OA不是ERP，不抢金蝶/用友饭碗 |
| 社交化协作(类钉钉群聊) | 直接用微信/企微，不重复造轮子 |
| 原生App(iOS/Android) | 企业微信H5 + PWA 足够 |
| 完整的客户门户 | 二期需求，MVP阶段不碰 |
| 国际化(多语言) | 中小律所无此需求 |
| CalDAV日程同步 | 替代方案多，优先级低 |

| **资产化** | 文书在线编辑且版本不乱 | ONLYOFFICE编辑+版本追溯 |

| **财务透明** | 钱从哪来到哪去清晰可见 | 三表(回款/账龄/利润)可导出 |

## 九、深度讨论精华摘录

### R1 核心诊断
> 如果你想卖给小所：你打不过Alpha，因为他们有海量法律数据集成。
> 如果你想卖给大所：你的文档管理和移动端能力太弱。
> 建议方向：停止在基础CRUD上打磨，立即攻克文档在线协同和移动端。

### R2 案件管理
> 系统目前是"数据仓库"，而不是"副驾驶"。它等着律师去填数据，而不是主动告诉律师该做什么。
> 律师最怕的三件事：错过开庭、漏掉上诉期、冲突当事人撞车。

### R3 财务管理
> 律所的资金流高度"事件驱动"和"收付实现制"。
> 合伙人只在乎两件事：钱（财务表现）和命（风控表现）。
> 金额存储绝对不要用float，必须用int64（单位为分）或decimal库。

### R4 文档管理
> 律师经常在微信、邮件中传文件，导致"初稿""修改稿""最终定稿""打死不改稿"满天飞。
> 知识库的核心是"结案时强制提取争议焦点/法官倾向/代理策略"。

### R5 移动端
> 移动端做"减法"，只做"确认、查看、提醒、紧急操作"。
> 不要试图把桌面端所有功能搬上手机。

### R6 审批流程
> 审批人看到的只是一个审批单，看不到业务细节——这是律师不爱用的根本原因。
> 让审批人能在30秒内看完背景、问清问题并点下通过，审批系统才会真正跑起来。

### R7 冲突检测
> "股权穿透盲区"是最大的合规风险。如果律师代理A起诉B，B是大客户C的全资子公司，不穿透就会"自己打自己"。
> 案件进行中新增当事人不触发二次检查，可能导致律师被法庭要求撤出代理。

### R8 数据安全
> 当前最大漏洞是"纵向权限过宽与横向隔离缺失"——普通用户可能通过遍历URL查看不属于自己的案件。
> 审计日志必须覆盖"只读操作"，每次脱敏转明文必须强制记录。

### R9 第三方集成
> 天眼查集成核心逻辑：将"录入员"的角色从律师转交给API。
> 电子签章严禁自建，法律效力核心在于"第三方存证"和"CA证书"。
> AI真需求：长文档摘要、结构化提取；伪需求：自动写起诉书。

### R10 终局建议
> 1. 业务大于技术：一份漂亮的冲突检索报告PDF，价值远高于微服务架构。
> 2. 警惕功能蔓延：做"通用模版"引导用户适应系统，而不是让系统适配所有奇怪习惯。
> 3. 重视实施成本：实现Docker一键安装和极简UI，减少后期运维量。
