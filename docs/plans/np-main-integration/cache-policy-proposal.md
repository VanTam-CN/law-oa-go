## 3. 三种可选方案

| 方案 | 收益与代价 | 本轮建议 |
|---|---|---|
| 仅删缓存里的 description | 改动较小，但标题、主体名称等仍可残留，需逐字段识别全部正文载体 | 不作为真实资料首批试用默认方案 |
| 接案业务内容仅内存，保留最小恢复标识 | 避免表单/源包落 Web Storage；刷新会丢失未保存文字，需要明确提示与原生保存 | **推荐**，范围明确，能保留已验证的断线回查机制 |
| 本地加密正文或服务器自动草稿 | 密钥、清理、权限、版本及恢复成本显著增加；会形成新的写入和恢复链 | 本阶段后置 |

没有设计“页面内置密钥加密”等同于终端保密的承诺；也不以浏览器退出自动清理作为唯一保护。

## 4. 数据放在哪里

| 数据 | 推荐位置 | 生命周期/读取规则 |
|---|---|---|
| 正在输入的表单、对话、候选、原句、来源选择、冻结请求正文 | 当前页面内存 | 保留人工输入；账号/对象切换需明确处理未保存内容；退出/卸载后失去恢复能力，不另存 sessionStorage/IndexedDB |
| 已保存草稿、revision、不可变来源、终态回执/墓碑 | 原生服务端 PG | 重新鉴权后按原生路由读取；缓存策略不删除来源、回执或墓碑 |
| 未决保存恢复标识 | localStorage 中独立、带版本的最小标识记录 | 只含 request_id/action/intake_id；账号隔离在键空间，不含标题、姓名、正文、候选、令牌或源包 |
| 登录 token/用户信息 | 现有认证存储 | 本轮不重构认证；共享试用终端按已有入口不记住登录，但这不是正文缓存策略的实现 |
| HTTP 响应正文 | 不进入接案业务响应缓存 | 相关路由显式禁止缓存读取和写入，并返回 Cache-Control: private, no-store；每次重新鉴权 |

恢复标识不授予对象权限。账号 B 不展示或使用账号 A 的标识；A 再登录后仍可凭原键回查，服务器继续校验当前身份与对象权限。无权限时不展示案件名称/来源，不因 401/403 删除原键。

## 5. 交互与防丢失规则

1. 表单明确提示“本页未保存文字不会在刷新后恢复，请用保存草稿”。提示不能写成“已自动保存”。
2. 原生保存成功必须以真实回执、revision和重新打开结果为准；恢复成功不自动应用旧候选或覆盖已编辑文字。保存/回查/放弃的终态须匹配原request_id和对象ID，action如有返回也须一致；committed/no_change的revision须满足服务端版本合同。缺项、错配、无法识别的终态均按未知处理，保留本请求恢复标识与输入，不自动换键。身份信息应与本次发出的请求快照比较，不能误用切对象后的当前页面状态。
3. 未保存时，应用内离开/切草稿/切账号提供现有确认入口；浏览器关闭提示只作辅助，不承诺所有关闭场景都能拦截。
   退出必须始终可完成；用户可明确丢弃本页未保存文字后退出，不能强迫其保存或等待网络恢复。退出只清本页内存与认证，不等于向服务端放弃原保存，未决恢复标识继续保留。
4. 保存结果未知时，原键与 frozen 正文在同页保留；不允许改变正文后生成新键重发。
5. 刷新/重登录后只有恢复标识，没有冻结体：只能回查或明确结束原保存；不能凭当前新页面重新组装原请求。
6. GET返回unknown不删除标识。身份匹配的committed/no_change才清理对应记录并引导重开；明确放弃必须走原POST协议，让服务端写墓碑或返回已有结果，核对返回身份后才能清本请求记录。abandoned无保存revision要求，不能把GET查询当作放弃。
7. 对话过期、助手关闭、退出登录、空闲 TTL 和一般缓存清理都不能顺带抹掉未决恢复标识；也不能自动结束保存。
8. 浏览器禁用存储、配额耗尽或标识写入失败时，严格保存请求不得发出，避免制造无法回查的业务写入。页面内容仍保留。
9. 用户手动清站点数据、无痕会话关闭等超出应用控制的动作可能丢失恢复标识。没有服务端列表能力时不能承诺找回原键；不得据此自动换键。

### 5.1 保存中编辑、退出与重载（MI-R04）

- 发出保存时冻结请求正文/来源选择并记录当前编辑版本。允许继续输入时，新文字不得进入原键重试体；原请求终态只确认当时保存的A，不确认后来输入的B。新输入使旧来源候选失效，沿用既定人工文字优先规则。
- “保存并退出”只有当前编辑版本仍等于保存快照时才能在成功后退出；期间有新输入则留页、保留新文字，分别显示“原请求已保存”和“当前还有未保存修改”。不能把A的回执当作B已保存，也不能靠页面卸载清空B。
- 同一规则适用于断线后的回查/放弃回包；若保存已提交，仍保留后来输入的B，后续另存须先核对真实服务端版本，不能盲目自动再次PUT或以A覆盖B。
- “重新加载服务端草稿”发请求前检查当前未保存文字，明确说明将替换内容，用户取消则不替换；用户确认后仍记录编辑/导航版本。请求期间又输入C、切对象或账号时，晚到响应不得覆盖；保留C并提示需重新核对。只有获确认且期间无新编辑时才替换、更新已保存投影和来源状态。
- 刷新/关闭仍可能丢失未保存内存，这是明确的产品取舍，不能用后台自动保存、正文持久化或新增确认执行器来补范围。

## 6. 同源双标签：必须新增的恢复验收条件

### 回执夹具适配（M0-R04，I16/C04–C07）

源Hook测试的部分成功响应缺少对象`id`或`request_id`，并只检查旧单槽为空；这些夹具不满足本文身份核对规则，主干必须标为ADAPT，不宣称原样KEEP。

- 成功PUT/回查/放弃夹具回显实际捕获请求的`request_id`、`id`（服务端回执现有对象字段）；committed/no_change还要合法`revision`。恢复标识的`intake_id`与回执`id`比较，不能要求服务端返回不存在的同名字段；`action`仅在回执提供时比较。
- 保留原缺身份响应作为负向：保留原每请求记录、冻结体和人工输入，不解锁新键。unknown同样不解锁；不能只修正正常fixture而删掉缺字段场景。
- v2正向断言必须核对本请求对应记录被清、其他未决请求仍在；负向必须核对本请求记录原值仍在。仅检查旧`np-save:`槽位为null不足以证明新实现正确。
- 旧格式兼容、每请求键以及同context双页交错响应分别覆盖。历史22个Hook/5套33项只表示来源场景数，适配和新增负向后的实际展开数后续记录。

回执身份解析及相应fixture适配归M3；每请求存储、编辑防丢失及双标签行为归M4。M2消费完成的fixture执行完整I11，M5执行真实root入口，不重复计算同一实现。

### 6.1 静态证据与结论边界

现有流程为读取同一槽位 → 生成键 → setItem → 收到终态后 removeItem(槽位)。两个页面可能都先读到空槽；后写的标识覆盖前写；任一页面终态又可能移除另一请求的标识。

这属于源码支持的竞争路径推演，**本轮未执行真实双标签复现，不报为已复现的重复提交或数据库覆盖**。服务端版本与幂等保护仍在，不应由此推导业务表已经重复写入。它必须在下一阶段缓存改造中关闭。

### 6.2 最小推荐处理

- 恢复记录改为“账号+接案+request_id”独立键，例如 `np-save-v2:<actor>:<intake>:<request>`，值仍只有三个字段；不写一个会被整包替换的待办数组。
- 每个请求只清理自己的记录。发现其他未决请求时阻止新建保存，只提供逐笔回查/结束；在两个页面同时越过初始检查时，也必须保留两条记录，最终由服务端锁、revision 和回执裁决。
- 不把 localStorage 的先读后写或比较后删除当作跨页面原子锁；不为此新增分布式任务平台。
- 旧 `np-save:<actor>:<intake>` 只读兼容并按 request_id 去重。先确认终态才清对应旧标识；切换期间按§7先核对/处置旧内容，再关闭旧版本标签，避免老客户端继续按槽位写/删。不要在旧写入者仍活动时自动破坏性迁移。
- 无权限或数据格式异常时保留可核对标识、隐藏业务信息并提示处理；不能将“解析失败”默认为安全换键。

## 7. 历史正文与预填的处置

本阶段推荐**专用、新建的试用浏览器配置文件**，先确认没有旧接案缓存，再启用仅内存策略。这能减少首批试用的历史数据清理范围，不能代替已有终端的处置。

已有终端按以下顺序处理，均需操作者明确确认：

1. 先暂停旧标签发起新操作，保留页面，不刷新、不关闭。逐页记录原request_id并核实未决保存的真实回执；不删恢复键。暂停新操作不等于停止已发请求，需等待终态或由用户明确放弃并取得墓碑/已有结果；未知状态继续HOLD。
2. 在旧标签仍打开时，逐页核对仅内存文字、sessionStorage预填与本机暂存。需要保留的内容由有权律师核对，通过有权限、版本及来源保护的原生路径保存并重开；无安全保存路径时保持该终端HOLD，不为切换强制全量写入。不能把旧文字自动当作可信来源重新绑定。
3. 需要保留的内容已重开核对，或用户明确放弃本地未保存内容后，才关闭对应旧标签并确认不再有旧写入者。放弃本地文字不等于放弃服务端未决请求；无法核对/无法暂停的标签不切换、不启用新策略。不得先关闭再尝试找回仅session/内存内容。
4. 仅在确认后定向处理已知正文键：旧 v1、当前账号/场景的 v2、历史 conflictFingerprint 和预填。v1 不含账号，不自动判断归属；涉及其他账号的清理须有单独设备处置确认。
5. 不执行 localStorage.clear()/sessionStorage.clear()/清整个站点，不删无关模块、认证数据和 np-save 恢复标识。避免原有挂载时自动删除 v1 的副作用先于操作者核对。
6. 在仅内存试用模式，旧本机“恢复草稿”入口不读旧正文；从服务端恢复仍保留。已经存在的原生功能在其他构建中不被这份方案静默移除。

若整合候选保留源分支的预填入口，试用模式不得继续把 description 写入 sessionStorage。只有已存在、当前有权的服务端对象能用中性定位信息重新取数；没有服务端对象的临时预填不在此阶段增加跨页面正文传递能力。main 当前没有该预填存储入口，不为缓存方案新增它。首切片原菜单直接重开已有草稿仍可用。

## 8. HTTP/Redis 边界

- 同一显式排除规则覆盖`/api/v1/case-intakes`、`/api/v1/case-intake-assist`整个前缀，以及`/api/v1/cases/intake-workbench/:id`别名（main `internal/router/router.go:399`）。按实际路由路径/边界匹配，在全局缓存读取之前排除且不写响应缓存，包括详情、来源、回执、资格与错误响应；不能只在handler返回时才设置标志。
- M0枚举全部可返回同类数据的可达路径，M4逐项实现，I10/C10覆盖主路由与别名。Redis启用并预置旧正文，用业务响应缓存读写调用计数/探针验证均为零，同时核对双账号、撤权、版本变化和响应头；认证等合法Redis调用不应被误判为失败。别名遗漏是已确认的配置范围缺口，不宣称已复现缓存泄漏。
- 设置 private, no-store；仅设置响应头不足以弥补当前 TTL 实现。不要顺手修通用缓存使这些接口从“碰巧没缓存”变成可缓存。
- 不依赖 `X-Cache-Skip` 客户端请求头、空缓存、零 MaxBodySize、Redis 未连接或路由前尚无 user_id 来保证安全。
- Redis 用于现有认证/其他能力可继续；实际 main 与 Redis 联调必须证明来源读取、撤权和回执查询每次走当前权限，不命中旧正文。
- 不泛化为全站缓存改造；本次只明确接案与助手边界。浏览器返回/刷新/账号切换仍需实际检查，不能仅凭响应头推定没有残留。
