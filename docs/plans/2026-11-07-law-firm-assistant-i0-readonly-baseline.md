## 4. 窄版落地必须明确的契约

详细字段表、写入清单及物理结构建议见附录清单。以下为本次建议的收敛结果，尚未实施。

### 4.1 保存链路

继续只有原生 POST/PUT 两类业务入口；创建、更新分别构造 DTO。将接案权限、实际字段变化、revision、当前来源关联、快照及回执集中到接案应用服务。无需抽取全所通用应用框架。

本批律师试点的新建整理及对应草稿创建，必须先通过现有客户授权。人员助理的普通 assistant_draft 继续沿用原有无客户绑定规则，不能把试点前置条件套给所有原生 POST。对已有客户绑定的接案，更新总是复核数据库里的当前客户，不允许通过省略 client_id 跳过。带来源保存仅限 draft；正式流程仍在原页面，不能为了保存把已推进对象退回。

所有接案写入均参加版本控制。长时间检测不能从完成时重新读取版本后直接标记为最新；必须携带最初检测输入的版本，拒绝基于旧事实的结果覆盖。同步路径两次 metadata 回写应合并为一次受控写入。

同键重试：先校验当前权限并核对摘要、目标及动作，再查询持久化结果；已有结果不依赖内存上下文仍然存在。没有结果不等于可以换键再次创建。no_change 也有原键结果。

### 4.2 多轮与来源

保留 v0.2 的三种独立版本：业务 revision、临时 context_version、页面字段编辑序号。不得用一个内容散列代替三者。

- 只有服务端接收的真实原话/更正/选择可以构成来源。
- 结果交付和保存接受点均重新检查上下文与权限。
- 保存接受点复制不可变来源包并冻结上下文；不在模型或 PG 等待期间持有上下文互斥锁。
- 保存前更正成功使旧候选失效；保存已接受则拒绝后来的更正进入同次提交。
- 人工改字后来源逐句支持不再自动成立；用户明确选择背景关联或未关联。
- 历史快照与当前适用索引分开；A→B→A 不恢复旧来源资格。
- 暂存上下文失效不能让已保存来源失效；模型开关关闭也不关闭经授权的历史来源读取。

### 4.3 登录会话：采用当前 access 会话绑定

当前已有 auth_token_sessions 和自定义 UUID，可复用，暂不建设跨刷新会话族。

建议可信绑定为：账号 ID + 已验证的 access UUID + 对应数据库会话行 + 有效期，再绑定客户/接案。不接受前端自报 session_id；核验账号仍有效、试点白名单及当前角色/对象权限。

刷新得到新 access UUID、重新登录或换设备，均不自动接续旧临时上下文。旧 token 若服务端仍有效，其绑定的旧上下文按原有有效期/撤销规则处理；不能声称刷新已自动撤销所有旧 access token。登出或撤销哪个有效会话，必须由服务端状态决定，清空浏览器不等于服务端撤销。

敏感试点路径不接受“没有会话行但签名有效”的兼容令牌。全局 access 类型限制属于小范围共用入口修正，需回归现有登录与调用方。Redis 失败、数据库不可用、用户/设备撤销均应有明确拒绝和回归；不扩成全所认证重建或刷新体系重做。

### 4.4 当前卡点与草稿恢复

当前卡点仅根据当前接案、明确角色/指派字段和现有合法动作计算。草稿创建人、metadata.lawyer_id、实际当前处理人并非天然同一人；没有可靠依据就显示“待分配/待核实”，不能从标题推断。

建议复用 /case 案件中心容器，新增经授权的接案草稿列表及 /case/create?intake_id=... 恢复入口，由服务端 GET 恢复真实对象、revision、子项 ID 和来源状态。现有读取最多返回 20 条主体/材料：必须提供完整分页/明确覆盖标志，不能将截断集合当全部后再保存。

临时对话、来源片段和候选资格禁止进入浏览器持久存储；已经应用到原生表单的标题/摘要，v0.2 允许沿用现有本地草稿但要求单独核验。全面取消原生本地草稿属于另需裁定的产品变更，本估算不以删除旧草稿为前提。旧副本不得自动恢复为当前服务端版本、有效来源或已核对状态。

为便于复核去重：W07 分为入口/恢复 2–3、局部请求/主体编辑 3–5、存储/结果状态 1–2、作者契约验证 1 人日；W08 分为交互实现 5–7、作者组件验证 1–2 人日；W10 分为 PG 并发/故障/恢复 2–3、真实浏览器全链 1–2、独立复核 2 人日。W10 不再重复作者组件测试。

其中 W02+W03+W07 共 22–35 人日属于原生保存、入口和页面基础整改，尚未计算来源新增。这解释了为什么产品范围缩窄后，工程量没有按功能列表等比例下降。

人日是各角色总投入，不是日历天；不能简单除以人数承诺交期。如隔离 PG 验证暴露历史数据或并发模型问题，需单列增量和重估，不挤进固定缓冲。

### 6.2 哪些发现会触发重估

- 实际必须多实例/无中断滚动发布，且不能接受临时上下文丢失。
- 旧接案/主体数据无法稳定识别 ID、存在跨对象污染或需大范围清洗。
- 必须兼容多个未知全量 PUT 客户端而不能同步升级。
- 来源必须扩成附件、整段聊天长期归档、任意字段/跨案件追溯。
- 业务要求继续在刷新后恢复同一临时上下文，或全所统一认证迁移。
- 实际日志链无法做到内容禁记，或当前部署无法提供隔离验证环境。

这些是重新评估条件，不是本次已发现必须发生的工作。

## 7. 验收差距与下一轮最小证据

| 门禁 | 本次可提供的证据 | 未完成部分 |
|---|---|---|
| G00 | 当前源码指纹；写入口/页面/字段清单；PG 方言选择；会话/来源结构建议；日志风险及估算 | 可复现候选、实际 schema/拓扑、待决字段和锁顺序、运行环境证据 |
| G01 | 确认现有原生保存不具备完整版本/幂等/来源事务 | 全部实现与 S/D 运行断言 |
| G02 | 定位实际认证/日志/存储入口，避免只修未挂载中间件 | 授权/会话/日志哨兵/撤销与浏览器存储验证 |
| G03 | 多轮与覆盖保护无实现可验 | Stub 契约和浏览器断言 |
| G04 | 现有“恢复草稿”测试主要是 Mock+localStorage，不能证明本门禁 | 同候选浏览器→真实服务→隔离 PG 的完整闭环 |
| G05 | 已有要求可直接复用，无真实模型结果 | 至少 20+10 任务及独立语义评价；不能将结构合法当可用完成 |

后续最有区分力的验收不是截图，而是：

1. 只应用摘要后保存，原主体真实 ID/受保护身份引用、关系、材料、负责人和未知 metadata 均保持；人工显式编辑子项时又能正确改变。
2. 两个页面同时编辑，后提交者得到可恢复冲突；不能静默覆盖，也不能丢掉尚未保存文字。
3. 老检测在新版本后返回，不覆盖新事实、来源或状态。
4. 同键同参/异参、保存后断线、no_change、进程重启分别核对业务行、快照、当前关联及回执。
5. 当前客户撤权后，稀疏 PUT、旧保存结果回查、来源读取、上下文访问均拒绝。
6. 更正先到/保存先到两个执行顺序，数据库文字和来源均对应同一已接受口径。
7. 手工 A→B→A 后旧来源不复活；相同文字不能取代确认记录。
8. 新浏览器或清空本地内容后，从菜单恢复同一服务端草稿；超过 20 个子项不能被截断后删除。
9. 用虚构哨兵覆盖慢 SQL、SQL 失败、模型异常、请求/代理/浏览器存储；业务内容不得进入诊断日志。
10. 关闭模型后仍能正常人工保存、读取既有来源；失效的未保存聊天不伪装恢复成功。

这些不替代 A01–A40，只是下一轮优先取证顺序。全量适用断言仍按 v0.2 分层执行，20+10 技术评测与 24 对律师模拟任务分别计数。

## 8. 是否还能保持窄版：三个选项

| 选项 | 产品结果 | 工程判断 |
|---|---|---|
| A：保持完整 v0.2 | 对新建及已有 draft 完成对话→核对→原生保存→来源/菜单恢复 | **可保持业务窄版**；接受 48–76 人日基础估算及原生整改，先闭环 G00 后分段实施 |
| B：重新审定为“只新建草稿” | 先验证新资料整理，暂不从已有 draft 发起助手 | 可能减少已有草稿映射与部分交互，尚未细估；仍须防止保存后被原生入口覆盖，不能免除权限、日志、来源和其他写入版本规则 |
| C：只做不落库的交互/语义验证 | 虚构案情多轮整理，人工查看输出 | 可以更早验证问答负担和摘要质量；**不满足 v0.2 的真实业务闭环与来源恢复目标**，不能作为它的通过证据 |

本次建议：保留 A 作为完整试点候选，把基础整改明确作为第一段项目，而不是隐藏在“助手开发”里。若投入上限仍是两三周，应重新讨论 B 或 C，不能直接删掉已有草稿场景或降低覆盖保护来宣称 v0.2 已实现。
