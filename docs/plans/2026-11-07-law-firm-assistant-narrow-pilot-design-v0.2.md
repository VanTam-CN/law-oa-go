## 1. 目标、完成条件与后置范围

### 1.1 一次任务何时完成

必须同时满足：

1. 对象正确：开始整理前客户已由律师在原控件明确选择并通过服务端授权，新建表单或指定接案草稿清楚绑定。
2. 内容正确：标题/摘要来源可查看，已有关键事实有正确去向或明确的人工不纳入记录；冲突、未知和模板建议没有被写成已核实事实。空泛但无明显错误不算完成。
3. 应用受控：只应用律师选择的字段，未选择和已有人工内容保持原值。
4. 保存真实：原生接口返回实际对象 ID、保存 revision 和来源保存状态。
5. 结果可恢复：原菜单读取服务端同一草稿；在有权限时能回看保存的来源快照及其适用范围。
6. 不产生非预期影响：未自动修改主体、材料、人员或正式办理状态，未重复创建或静默覆盖。

仅生成文字、应用到前端或展示成功气泡都不是任务完成。

### 1.2 本批功能

三个功能组成同一条窄链：当前对象办理情况；多轮文字整理；候选核对后进入原生保存。保存后的必要来源读取是本批追溯要求，不包含全量聊天恢复。

明确后置：第二套模板、跨对象聊天、全局今日工作聚合、语音/OCR/PDF 解析、文件管理 F0、文书输出、正式检测/审批代操作、长期聊天历史、自动提醒、后台重启接续、外部 MCP、多智能体及多律所 SaaS。

### 1.3 模板使用边界

首套模板固定 ID 为 sale-contract-intake，版本初始建议为 1.0.0。律师主动选择或确认模板；其展示的是整理方式，不作争议性质裁定。案件类型候选映射到当前枚举 commercial，由原控件明示并经律师确认；AI 不生成 case_type 写命令。原草稿已有其他类型时不得静默改类型，需重新确认适用性或退出本次整理。

模板事实槽位：交易角色、相对方叙述、交易依据、交易标的、履行情况、付款情况、争议与诉求、已知程序情况。无正式字段的要素仅用于摘要或临时核对，不写入隐藏 metadata 或主体/材料字段。

## 3. 人员、对象与办理状态

### 3.1 身份和权限

试点资格是“白名单 + 真实律师角色 + 当前动作权限”的交集。白名单不扩大权限，管理员身份不自动获得案件内容。服务端从认证上下文取得人员身份，不接受模型或请求正文自报角色、所有人及已确认事实。

原生保存授权不依赖请求字段是否出现。更新时须在事务中基于当前数据库记录校验当前接案、当前客户和实际动作；仅更新标题/摘要或客户端省略 client_id 也不能跳过。新建时校验选定客户与创建权限。改绑客户时，先通过原对象/原客户授权，再检查目标客户与改绑权限；任何一项失败，正文、来源和成功回执都不能提交。此规则适用于原生手工和带来源保存，不以是否启用助手区分。

创建上下文、每轮取数、结果交付、应用前读取、原生保存及来源读取都重验相应权限。临时上下文仅能由发起账号及绑定的有效认证会话访问；登出/会话失效后不能凭 context_id 恢复。对象撤权后不再返回标题、片段、计数或错误细节；已显示到浏览器的内容无法保证被远程收回，应清空当前助手显示，不能承诺消除用户已有副本。

### 3.2 客户选择与对象绑定

| 入口 | 绑定 | 处理 |
|---|---|---|
| 未选择客户的新建页 | 不创建整理上下文，不接受助手轮次 | 提示先选择已有客户；仍可手工填原生表单，不提前发送其内容给模型 |
| 新建接案，已选客户 | 服务端授权后绑定随机 context_id、页面 form_instance_id 和明确 client_id | form_instance_id 仅作关联，不是授权凭据；不生成假业务 ID，不允许后补初始客户绑定 |
| 编辑已保存 draft | 真实 intake_id、服务端 revision、当前可读/可写字段 | 授权后从服务端读取，不以名称匹配或本地副本推断 |
| 新建保存成功 | 使用真实回执中的 intake_id 和 revision | 本次上下文结束；继续整理需基于新版本重新开始，不能把旧上下文静默改绑 |
| 切换客户、对象或模板 | 未保存阶段结束旧上下文；保存处理中禁止该次整理改绑 | 保留表单文字供人工对照但移除旧候选可应用资格，显式提示旧文字属于原对象；不得自动搬入新对象或沿用旧来源，新整理重新授权开始 |
| 补正模式、人员助理草稿接手、非 draft 状态 | 本批不启用候选应用 | 可展示有权查看的当前状态及原生办理入口，不自动退回草稿或接手所有权 |

正常首轮顺序固定为：进入原生页 → 人工选择库内客户 → 服务端授权 → 选择模板/开始整理。选择其他客户再选回原客户，也不复活已经结束的上下文。新建时负责律师仍由原生控件决定，在原生保存前按其必填规则检查，不由模型推断。

已有来源快照的接案，本批禁止通过普通原生编辑改绑客户，包括手工保存和带来源保存；这防止按新客户权限读取旧来源。此约束适用于已有任一来源快照的记录，不因覆盖状态为“未关联”而绕过。无来源历史的旧草稿改绑按原生规则且同时校验原对象/原客户和目标客户；进行中的整理必须结束。若律所要求转移已有来源记录，另定授权与历史可见性流程，不属于本批。

现有 source case / supplement 关联不在本批模型写入范围。外部 ID 使用现有真实 ID 的规范化字符串；不得因本稿约定改变客户原控件/后端 ID 类型。

### 3.3 保存条件与资料完整性

模型和模板的未知项不自动阻断草稿。草稿保存必须满足实际原生业务契约；目前页面所读路径会要求律师选择库内客户和负责律师，服务端对应要求仍需 I0 确认。正式检测必填项不能整体变成草稿必填项。原生接口拒绝时原样保留用户输入，并定位可公开的字段问题。

## 4. 页面与用户操作

建议原接案页保留四个区：原生表单、当前办理情况、临时对话/事实卡、候选差异与应用。助手侧没有保存按钮。

面向用户的动作：开始整理、继续补充、暂时不知道、先整理现有信息、查看原文、说明这是更正/后续事件/仍有争议、保留现有字段、选择替换、应用选中字段。原生保存使用原按钮。

固定提示：

- 整理结果：根据本次输入整理，尚未完成事实核验。
- 已应用：已应用到表单，尚未保存。
- 来源已保存：本次选中的录入来源已随草稿保存，可在有权限时回看。
- 部分无来源：本字段包含人工修改，相关原文仅供背景核对，不能表示逐句对应。
- 临时内容：未随草稿保存的对话在退出、过期或服务重启后可能丢失。

来源与错误不能只用颜色表示；键盘可打开/关闭来源和差异区，焦点回到入口。聊天输入不能夺走正在编辑表单的焦点。一个字段应用失败不静默应用其余字段：先让用户看见失败项，再明确选择可用字段。

## 5. 多轮对话行为规格

### 5.1 每一轮执行的动作

1. 验证当前用户、绑定客户/对象、模板、预算、expected_context_version 及上下文是否可接受输入；不合格时不接受轮次或发起模型调用。
2. 在上下文同步边界内接受原始文字或口径选择，分配真实 turn_id/动作记录，推进 context_version，保留实际录入人及时间。
3. 模型在有界上下文内提取事实、提出信息关系和候选摘要；无业务工具调用能力。
4. 服务端校验输出结构、允许字段、来源定位及引用关系，计算模板待核实项。
5. 展示“新增/补充、拟更正、可能冲突、仍未知”，更新候选区；不修改原表单。
6. 根据优先级展示最多 2 个问题；律师可一次回答多项或结束追问。

每轮都使用原始输入和已核对的事实结构，不能仅把上轮模型摘要当作新的事实来源。助手自己提出的问题、摘要和材料建议不是独立事实依据。

### 5.2 追问次序

优先级依次为：影响当前对象/交易角色的歧义；金额、时间、履行等关键事实的不同说法；影响摘要理解的缺项；一般模板建议。已经回答、标记不知道或跳过的问题不重复追问，除非律师新增信息使其重新产生实质歧义。

“先保存”“就这些”“暂时不知道”等表达触发停止继续追问的建议，展示已有候选；不自动应用或保存。遇到明确的模板不适用，提示检查模板并停止生成可应用的误导性候选。

### 5.3 信息关系与人工选择

| 情况 | 建议处理 | 不能做的事 |
|---|---|---|
| 后来又付一万元 | 提议为新事件，显示时间和原文 | 单看数字不同就判矛盾，或无依据补付款日期 |
| 前面说错了，应为四万元 | 展示拟更正前后，律师选择“按本轮更正”后形成已选的整理口径 | 模型自己宣布原错误已被事实核验推翻 |
| 甲称四万元、乙称五万元 | 并列为不同说法，等待核实 | 自动选择最后一句或较高“置信度” |
| 大约四五万元 | 保留估计和范围 | 写成确定四万元或五万元 |
| 没看到签收单 | 标记材料尚未看到 | 写成未交货或未签收 |
| 不知道是否起诉 | 程序情况未知 | 写成尚未起诉 |

模型提出的更正/时间关系先显示为候选关系；对将矛盾收敛为单一说法的操作，由律师在事实卡明确选择，服务端记录该选择。仍有争议时，可生成并列待核实的中性摘要，不能生成无保留的单一事实。

如果被更正的说法已经应用到表单，表单文字仍受保护，不自动改写；同时明确提示“表单仍含已被更正的旧说法”。旧候选不能继续按有效最新口径附带来源保存，律师需对比后应用新候选，或明确改为保留争议/人工表述及相应来源状态。通用“请核对”不能掩盖这一具体冲突。

### 5.4 临时状态

上下文状态仅表示整理过程：收集信息、生成中、可查看候选、部分候选过期、保存中/结果待核实、已结束/已过期。表单是否应用、业务是否保存及正式办理状态分别显示，不能用一个“完成”混淆。

多轮不是通用会话平台：不跨客户，不建立长期会话列表，不自动继续已超时任务。原生保存期间界面冻结该次提交快照，服务端也按第 5.5 节冻结同一上下文；其他标签页不能绕过。新的输入和应用在提交结果明确后进行，防止“保存中再改、成功后以为新内容也保存”。

### 5.5 对话版本、候选资格与保存接受点

业务 revision 保护已保存接案；context_version 保护本次尚未保存的输入和整理口径；字段变更序号保护当前浏览器人工编辑。这三个值不能互相替代。context_version 由服务端从 1 起单调推进，客户端只能回传预期值，不能指定新版本。

| 事件 | 服务端版本/状态规则 |
|---|---|
| 接受一轮新输入、口径选择或明确不纳入选择 | 必须匹配 expected_context_version，接受后推进版本；同轮同 request_id 同参数重放不再次推进 |
| 发布一次模型结果 | 仅当前 generation_id 且基于仍有效的输入版本时发布，发布推进版本；旧响应丢弃，不能覆盖较新口径 |
| 生成中再提交轮次或保存来源 | 返回 CONTEXT_BUSY；不接受第二轮，不开启另一模型请求，不冻结来源保存 |
| 用户更正影响旧候选 | 原候选内容不可变，但其适用资格失效；已应用字段具体提示旧口径，不自动改表单 |
| 新轮次完成后使用旧轮候选 | 原有勾选/核对标记失效；律师须在当前版本重新对照。服务端检查所引事实是否被更正/撤回；受影响旧候选不能以 candidate_sources 模式保存，可改用新候选或明确人工背景模式 |
| 结束、取消、失效或切换绑定 | 推进版本并终止旧资格；取消不构成对业务事务的撤销 |
| 接受原生带来源保存 | 在上下文短临界区内比较版本和资格，复制不可变来源包并标记为保存中；冻结包记录接受的 context_version，进入保存中本身不重新解释事实 |
| 保存已提交 | 结束该上下文；后续基于真实 intake_id/revision 新建上下文 |
| 已确认整笔事务未提交/已回滚 | 若上下文、权限仍有效则解冻并推进版本，旧保存选择失效；重新对照后才允许新的保存意图，否则结束或转人工 |
| 结果暂不明确 | 保持查询原请求的状态；不解冻为可换键再保存，不把未知当失败；上下文到期可清除，原请求结果仍从持久化记录查询 |

候选保存 generated_from_context_version、事实依赖和服务端 ID；上下文发布版本与候选生成基线可不同。标题、摘要可来自不同轮的不可变候选，但保存时统一对照当前 expected_context_version，各自资格都须有效。人工关联原文只作背景，不能通过换模式把已纠正旧说法重新标为事实已核验。服务端只能确定结构、引用和已记录选择的一致性，不能自动保证所有自然语言语义正确。

**保存接受点**是服务端在同一上下文同步边界内“确认当前版本/资格＋复制来源包＋标记保存中”完成的时刻。更正先完成，旧版本保存拒绝；保存接受点先完成，之后的更正、其他新保存键、应用前读取为可应用状态或普通取消均返回保存中，不能进入本次结果。同账号其他标签页也遵守该规则。只读状态及结果查询允许，但仍需授权。

不跨模型调用或数据库等待持有上下文互斥锁；复制后使用独立不可变包，异步清理 TTL 不破坏已接受包。保存业务事务仍在自己的最终授权/状态/revision 检查点决定是否提交。冻结不赋予数据库写权，也不阻止其他正常业务入口推进 revision。

同一保存键、同一规范化参数的并发调用归并为同一保存；针对该上下文的新保存键在保存中拒绝。同键异参（含不同 context_version/候选/来源模式）拒绝。丢响应后先处理已持久化结果，再考虑临时上下文；已知回滚后的新保存需重新核对并使用新保存意图。进程重启不恢复未保存上下文，不建设后台租约或恢复平台。

该冻结限制本次上下文的操作，不声称锁住整所原生业务。其他有权原生入口仍受业务 revision 和状态约束；无上下文的纯手工保存不因此被当成对话动作。同一表单保存结果未明时，前端必须保留原请求键、禁止换键或转人工重复提交；服务器不能仅凭案情相似认定两个不同的新建意图是一次重试。

## 6. 完整虚构示例

### 6.1 第一次输入

律师已在原生控件选择并获准访问甲公司，确认本模板；系统才建立绑定甲公司的上下文。以下金额和主体均为虚构。

律师：“客户甲公司说，给乙公司供应了十二万元的设备，乙公司先付了四万元。双方有书面合同，甲公司想追回剩余货款。我还没看到乙公司的签收资料。”

助手按原意展示供货、付款、合同及签收资料情况，问：“合同付款时间是否清楚？目前是否已经起诉？”同时允许“先整理现有信息”。不自动计算法定期限，也不把未看到签收资料认作未签收。

### 6.2 第二次补充

律师：“乙公司后来又付了一万元，目前总共付了五万元。还没有起诉，付款时间我现在不清楚。”

助手展示“先四万元、后增加一万元、目前累计五万元”的提议，分别引用两轮原文；程序情况只标为“据本轮录入，尚未起诉”，不改 OA 的案件/接案状态。

### 6.3 第三次更正

律师：“更正一下。我刚看了付款记录，第一笔其实是三万元，第二笔一万元，总共四万元。前面说五万元是我记错了。”

助手展示五万元到四万元的拟更正。律师点击“按本轮更正”。系统记录本次选择及前后输入片段，并注明“律师表示看过付款记录；系统未读取该记录”。

候选摘要：“据本次录入，甲公司称向乙公司供应价值十二万元的设备。律师后续更正称，乙公司第一笔付款三万元、第二笔付款一万元，累计付款四万元。双方有书面合同，合同付款时间及乙公司的签收情况待核实。律师表示目前尚未起诉。甲公司希望追回剩余货款。”

### 6.4 应用及保存

标题已有“甲乙设备货款事项”时默认不替换。案情摘要已有文字时先对比，由律师选择保留或替换。本例律师保留原标题、选择摘要候选并核对来源，点击应用；此时只改变本地摘要，显示尚未保存。原生保存成功后显示真实草稿编号、revision、来源状态；重登通过菜单读取相同 ID 和保存文字，再打开来源。

若律师未解决四/五万元的分歧，则候选应并列两种说法；只有律师明确选择暂不纳入确定数字时才可省略数字，并仍保留付款情况存在争议的说明。测试不能只覆盖本例的顺利更正。

## 7. 事实与来源契约

### 7.1 三个不同维度

| 维度 | 取值及含义 |
|---|---|
| 输入来源 | 本轮律师输入；前轮律师输入；经选择纳入的当前草稿字段；模板建议 |
| 整理情况 | 有输入支持；未知；不同说法待核实；提议更正；律师已选择整理口径 |
| 核验情况 | 默认未作客观事实核验；“已核对本次录入”只证明人员作过核对选择 |

不得用一个 known、已确认或百分比置信度同时代替这三维。金额/日期/主体关系的提取正确性需要人工及评测核对，不因原句存在而自动保证。

### 7.2 可核对的最小事实记录

临时记录至少包括：fact_id、槽位、整理文字、source_refs、可能的更正/后续事件关系、律师选择及选择时间。事实/候选 ID 由服务端分配或绑定到当前上下文和生成轮次，不能任由模型引用其他上下文同名 ID。source_ref 至少包含服务端 turn_id 或原字段引用、片段范围、完整引用文字、录入人及录入时间；模型不能自报录入人、确认人、来源类型或“系统已验证”。

已保存草稿字段只有在用户选择“纳入本次整理”且重新授权后才作为模型输入，范围限 title、description；记录实际原 revision 和原文片段。默认不把整个表单、关联案件或全卷宗送入模型。

### 7.3 原文定位和语义限制

- 对用户文字不静默去重、改数字、改否定词或修正文意；服务端保存当次接受的文字。
- 片段位置统一为 Unicode code point，起点含、终点不含；前后端显式转换，不能混用 UTF-8 字节或 JavaScript UTF-16 下标。
- 引用文字由服务端从已接受的源文字截取，并要求与模型引用逐字一致；引用需保留理解主语、否定、条件、单位所需的上下文。
- 无效范围、虚构引用、引用到助手自己文字、跨上下文 source_id 一律拒绝或重生成，不进入可应用候选。
- 摘要分为可定位片段，每段引用已提取事实；模板提示单独标注。模型不能用“据输入”包装新增法律判断。
- 精确匹配只验证出处存在，不验证片段是否支持该事实；“合同金额被当作已付金额”等错配必须在质量评测中单列。
- 首版不自动把推导出的余款、利息、法律期限作为事实。需要时保留原输入或提示人工计算核对。

### 7.4 模型输出边界

建议结构为：固定槽位事实、拟议信息关系、title 候选及来源引用、description 的分段候选及事实引用。服务端拼接已验证的摘要分段为 description；JSON Schema 在各层禁止额外属性，限制长度和枚举。

不允许模型输出客户选择、业务角色权限、写入掩码、清空授权、人员指派、操作 URL、SQL、材料/主体写命令、已保存或已通过检查结论。模型原始文本按纯文本显示，不执行 HTML/Markdown 中的脚本或外链动作。

### 7.5 关键事实去向与整理完成

事实核对区同时展示“已纳入摘要、待更正/有争议、未知、明确暂不纳入”。已经提供的关键主体、交易与付款金额、时间限定、否定和不同说法不能因压缩摘要而悄悄消失。最终拟保存文字应保留理解案情所需的关系；原文只在临时卡出现而最终摘要遗漏，不等于已经整理完成。

律师可逐项明确暂不纳入；服务端记录该事实、选择人/时间、必要理由和 context_version。批量笼统的“都不用”不能把空泛摘要变成可用完成；不得省去争议或否定后改变剩余文字含义。未解决争议可并列表述，数字暂不纳入时也保留存在争议的说明。未知项允许保持未知，不要求为了完整率猜测。

这些是产品行为和人工核对要求；技术评测的必需事实集合由独立业务标准答案预先确定，不能由被测模型自报“已覆盖”作为正确性证明。可用完成的定量标准与分母以 v0.2 验收第 5 节为准。

## 8. 来源留存：本稿建议选择的方案

### 8.1 选择与替代

本稿建议以“保存后仍可核对录入来源”为试点产品目标，选择最小来源快照。纯页面临时来源可用于技术演示，但不得作为具备事后追溯的等价交付。把整段聊天自动追加到 description 不作为默认实现。

需要新增的是一类业务来源快照和原生保存结果的必要持久化能力；物理表是否复用由 I0 判断。不能因为取消 assistant_operations 就认为数据库完全无需改变。

### 8.2 保存内容与排除内容

| 随草稿保存 | 默认不保存 |
|---|---|
| 最终实际保存的两个允许字段文字及受保护校验值、来源覆盖状态，用于历史出处对应 | 未应用的全部候选、其余表单全文和全量聊天 |
| 被采用或人工关联的必要原文片段与理解所需上下文 | 模型推理、完整服务商报文、密钥/令牌 |
| 与本次保存相关的必要前后更正片段、明确不纳入记录及律师选择 | 无关第三方资料、身份证件原文、无关未采用输入及非目标字段 |
| 实际录入人、原输入时间、核对动作人/时间 | 自动猜测的身份已核验或法律事实已确定标签 |
| intake_id、真实保存 revision、接受的 context_version、逐字段 candidate_id、模板/结构/模型配置版本标识 | 客户名称驱动的跨对象关联、完整外部材料副本 |

生成前提示避免输入身份号码、账户凭据等本任务不需要的信息；检测到明显不必要的身份标识时先拦截并提示删减。不能把简单检测宣称为完整脱敏。真实资料进入提供方的条件见第 12 节。

### 8.3 人工改动后的来源覆盖

服务端根据最终保存值和已存的候选计算真实状态，不信任前端自称完全匹配。

| 保存值 | 来源展示 |
|---|---|
| 与已选择候选逐字一致，关联有效 | 候选录入来源可查看；仍注明未作事实核验 |
| 候选后经人工修改 | 不自动沿用逐句对应；可由用户明确关联原片段为“人工关联，供背景核对” |
| 完全人工输入且未关联来源 | 标为人工录入、无关联原文；不生成虚假引文 |
| 字段未变化且原来源有效 | 可继承原来源，明示最初留存 revision，核对当前字段仍与绑定值一致 |
| 字段变化且无新来源 | 当前字段标记需要重新核对/未关联；旧快照仅是旧版出处 |

用户可以保存合法的人工修改，但界面必须让其看见来源覆盖降低。若请求仍选择 candidate_sources 而最终文字与候选不一致，或候选资格失效，服务端拒绝该次带来源保存；返回 SOURCE_COVERAGE_CHANGED 或相应失效错误，由用户重新选择有效候选、明确人工背景或无新增来源后再提交，不静默降级。此类人工改写任务在产品评估中不能计为“所有关键事实均具有自动逐句来源”的成功。人工关联不升级为客观事实证明。

### 8.4 数据结构与一致性

逻辑结构建议：

1. 现有 case_intakes：增加/统一整型 revision；同一事务维护第 8.6 节两个字段的当前来源关联索引，保持真实对象与权限语义。
2. case_intake_source_snapshots（拟名）：按 intake_id + saved_revision 唯一，记录两个允许字段的覆盖状态、必要源片段及更正选择。快照一经提交不覆盖成另一版本的来源；未关联也应明确记录状态。
3. 原生 case_intake_write_requests（拟名，可评估复用）：记录操作者作用域的幂等键、动作、规范化请求的带密钥摘要、结果对象/revision/来源快照引用及保存时间；不存完整请求正文。

这些是建议的逻辑责任，不是本轮创建了表。不能直接把客户专用幂等表当接案通用结果表，也不能把来源藏进现有 metadata 回避授权。

不要求每次无关状态更新都复制一份相同来源。原生对象读取应返回实际来源快照引用和逐字段适用状态：例如“来源留存于 revision 17，当前 revision 18 的摘要未变化”。不能直接用最新业务 revision 假定存在同号来源快照。查看历史快照时展示当时保存的字段文字，并与当前版本明确分开；旧出处不能因当前文字碰巧相似就自动变成新版已核对来源。

纯手工旧草稿无需回填虚构来源；读取显示“此前未留存录入来源”。从未留存来源的纯手工保存可以只维护未关联状态，不为不存在的出处制造快照；已有来源历史不能因当前指针为空就当作从未留存。新保存若仅改变其他字段，可继承有效来源；任何同对象写入口改变 title/description 时必须产生相应失效/新关联状态，不能留一个看似对应的新旧混合快照。

来源写入失败时，本次带来源的保存整体失败并回滚。服务端来源引用必须从本人的有效上下文解析，不能接受浏览器传来的任意原文冒充服务端已接收片段。允许人工新录入，但须以新的真实输入来源接受，不能冒充旧轮次或他人。

### 8.5 读取、保留与恢复

来源是接案内容的一部分。列表、摘要预览、详情、来源、缓存和错误均按当前对象及字段权限控制；来源按钮不能泄露隐藏字段。权限撤销后重登、换账号或猜 ID 都不能读取。关闭模型生成开关不应删除来源；原生页面应继续提供经授权的已保存来源读取。

临时输入过期可清理，已保存来源跟随律所确认的接案记录保留/删除政策及备份政策，不能套用临时 TTL 自动删除。政策、可读人员及服务商条件未明确前，真实资料试用 HOLD；虚构数据验证可先独立推进。隔离库中的保存、进程重启及数据库备份恢复应验证草稿与来源对应，不宣称生产灾备已经通过。

### 8.6 当前字段来源关联与跨版本继承

不可变历史快照与“当前字段是否还适用该来源”分别维护。每个目标字段至少有：text_revision（最近实际文字变化的业务版本）、coverage（candidate_sources / manual_background / unlinked）、source_snapshot_id 及快照内字段引用（无关联为 null）、binding_revision（最近关联建立/失效的业务版本）。物理列或同事务关联表由 I0 决定，不增加通用字段历史平台。

原生应用服务根据当前数据库文字、当前关联和本次合法来源选择计算转移。任何实际文字变化均推进 text_revision；任何来源建立/失效均推进 binding_revision，二者使用本次业务 revision。客户端不能指定旧快照为“仍有效”，也不能通过散列检索历史快照自动恢复关联。

| 保存事件 | 当前关联转移 | 历史快照 |
|---|---|---|
| 文字未变且没有显式来源动作 | 保留当前关联及 text_revision/binding_revision；若当前未关联，仍未关联 | 不复制无关快照，不按最新 revision 猜同号快照 |
| 文字改变且无新来源，包括明确清空 | text_revision 推进；coverage=unlinked，当前来源引用清空，binding_revision 推进 | 原快照保持原文字，仅供历史查看 |
| 合法候选来源与最终文字完全一致，引用资格有效 | coverage=candidate_sources；建立本次快照字段引用，binding_revision 推进；文字未变时 text_revision 不推进 | 创建本次关联快照，不覆盖旧快照 |
| 人工明确关联背景片段 | coverage=manual_background；建立新的关联，绝不声称逐句支持 | 保留必要片段和人工选择 |
| 人工改写后未重新选择背景关联 | 转为 unlinked；不自动继承原候选逐句引用 | 历史仅作旧版出处 |
| 其他原生入口改变目标文字或明确使来源失效 | 按同样规则在同一业务事务更新当前关联和 revision | 不保留看似仍对应的当前有效标记 |
| 文字再次变成历史上的相同值 | 仅按当前状态处理；unlinked 不因值相同变回 candidate_sources | 不查询“最相似/同散列历史快照”恢复来源 |

例：r17 的 A 有来源；r18 手工写 B 后未关联；r19 手工写回 A 仍未关联；r20 改无关字段继续未关联。该状态需经进程重启和原菜单读取仍一致。重新建立来源必须经新的有效上下文和明确来源选择，或明确人工背景关联；即使最终文字未变，也属于新的来源动作，需 expected_revision、幂等键、事务及新业务 revision。纯粹无文字差异、无来源动作的合法更新返回明确“未变更”，不推进业务 revision 或虚构新快照；仍在最终授权及版本检查后持久化本次 no_change 幂等回执，重放返回当时结果，不能只由前端判定后报已保存。

历史页面展示当年保存文字和覆盖范围；当前页只使用当前关联索引。证据包同时检查两个视图，不能仅比较字段散列。未保存的页面编辑后改回，仍按第 9.1 节保护候选应用；它与跨服务端多次保存的失效继承分别测试。

## 9. 防止覆盖：表单、对象和持久化三层

### 9.1 表单内的变更判定

为 title、description 分别维护初始值、字段变更序号、有无人工编辑/清空、候选基于哪个快照及已选应用状态。整体 form_instance_id/context_id 防错对象，字段变更序号防过期应用；哈希可辅助比较，但不是权限依据，也不能代替“曾被人工改过”的记录。

| 条件 | 应用行为 |
|---|---|
| 原字段为空且从未被人工编辑 | 可默认勾选候选，由用户点击应用 |
| 原字段非空，不论来源是否 AI | 默认保留原值；逐字段显示当前值和候选，需明确选择替换 |
| 生成时或生成后、点击应用前被人工改动 | 该字段 stale；重新展示对比，不能沿用早先勾选 |
| 人工清空后当前为空 | 仍受人工保护，不自动填回 |
| 模型未提供字段/null/空串 | 不产生删除/清空含义 |
| 再次整理或返回更晚候选 | 只更新候选区，已应用和手改表单不自动更新 |
| 重复点击应用 | 不重复追加，不改变未选字段 |

点击应用的当刻重新检查绑定、字段序号、允许字段及当前上下文授权。某字段已过期时先取消其选择；用户可以明确只应用其他仍有效字段。来源按实际应用后的字段关联，不能把整个表单统一标为 AI 已核验。

### 9.2 原生保存的最小变更契约

**本版选择显式局部更新，不再保留“或按兼容协议”的未决分支。** 原生 PUT 的 changed_fields 是必须遵守的更新范围，服务端仍逐字段授权并计算真实差异；它不是客户端自报授权。创建 POST 仍按新建 DTO 校验必填、角色和子项，不能拿创建的完整 payload 原样用于更新。两者复用同一应用服务的权限、来源及事务规则。

更新业务字段是现有原生允许字段的受控子集；I0 将实际字段、类型、可清空性、角色和正式失效规则列成枚举表。正式状态/审批等不能经模型或新 DTO 扩权。模型始终只提供两个字段候选，不产生下列协议动作。

| 请求规则 | 唯一处理语义 |
|---|---|
| changed_fields 未包含且正文未提供 | 保持原值 |
| 清单外携带业务字段，清单含未知/重复字段，或声明却没有相应值/动作 | 拒绝为 AMBIGUOUS_UPDATE；不得默默忽略或仍套全量 payload |
| 清单内标量字段 | 必须恰有一个非 null 的合法值，或在 clear_fields 中明确清空；服务端再校验字段与角色 |
| clear_fields | 是 changed_fields 的标量子集，不可同时提交该字段的值；只有字段可空且操作者有权才清空；必填字段拒绝 |
| 标量 null、空串作为隐式删除 | 拒绝；清空统一使用 clear_fields。正常非空案情文字不被静默修剪或重写 |
| metadata 变化 | changed_fields 含 metadata；正文只用 metadata_changes 的 set/remove 路径操作，拒绝旧的整包 metadata 替换 |
| metadata_changes | set 为明确路径和值，remove 为明确路径数组；路径须在本动作白名单，同路径/祖孙路径冲突、null 隐式删除或未知可写路径拒绝；未触达旧键原样保留 |
| 主体/材料变化 | changed_fields 含 parties/materials；正文使用对应 party_changes/material_changes 显式 create/update/delete 操作；旧的 parties/materials 全量数组在更新 DTO 中拒绝 |
| 子项操作 | update/delete 指定真实子记录 ID 并校验属于当前接案；同 ID 重复/冲突操作拒绝；update 仅改变其明确字段，保留原 ID/身份引用/关系；delete 必须显式并满足原生业务规则 |
| 新增子项 | create 沿用原生主体/身份保护契约，模型无写入能力；本地关联 ID 与真实 ID 映射及相关关系在同一事务维护 |
| 空子项操作集合、未提供集合 | 不表示“删除全部”；在清单内但无有效操作则拒绝歧义请求，清单外不发送 |
| 协议字段 | expected_revision、clear_fields、source_selection 等单列允许；只承担版本/动作约束，不能被写入 metadata 或业务列 |
| source_selection | 独立于业务字段清单，逐字段选择来源；允许为未变文字显式重新关联，但必须通过有效上下文、授权、版本及幂等检查；不提交即没有新的关联动作 |

子项的更新字段清单与清空规则同样显式，未知字段拒绝；I0 将其映射到现有身份、关系及材料校验，不以新协议绕过这些校验。负责人等非目标字段仍由原生控件主动编辑并按权限提交；AI 应用动作不得把它们加入更新清单。涉及已有来源记录改客户时，按第 3.2 节拒绝。

当前原生前端需要分别构造创建/更新请求；旧客户端缺少 revision 或仍发送全量更新应拒绝并提示刷新，不提供无保护旁路。此项是本批必要基础整改，不声称现有代码已支持。

本批必须验证：仅选择应用摘要、然后原生保存，主体 ID/身份引用、关系、材料记录、未知 metadata、负责人及原有非目标字段均无非预期变化。不能只验证最终页面名称相同；数据库需对照子记录 ID、受保护引用和字段内容。另以明确人工子项编辑作正向对照，防止通过禁用既有功能假装安全。

若 I0 发现该局部更新改造必须扩为大规模 OA 重构，先重新估算，或提出“仅新建草稿”的范围复审。没有复审不能删掉已有 draft 编辑场景，也不能降低覆盖保护标准。

### 9.3 数据库并发及其他写入方

更新必须以 expected_revision 原子比较并推进 revision；所有会修改同一接案保护字段、办理状态或相关来源有效性的入口都需参与版本协议。需清点事实确认、检测回写、冲突处置等原生写入，不能只给新接口加字段。非 draft 状态的助手保存要在事务内拒绝，避免页面打开时是 draft、保存时已被推进。

版本冲突返回明确错误，保留本地输入，读取最新服务端值后逐字段比较；不能自动以新 revision 重发旧的整张表单。旧客户端无 revision 的更新应拒绝并要求刷新，不能在旁路继续无条件覆盖。兼容上线及数据库变更需要另行批准，不由本稿授权。

## 10. 原生保存、幂等与真实回执

### 10.1 一次原生保存的顺序

1. 前端固定实际表单变更、逐字段来源选择、expected_context_version（有来源时）、expected_revision（更新时）及本次 Idempotency-Key；保存期间不混入新输入。
2. 服务端认证、校验请求协议并计算规范化请求的带密钥摘要。摘要包含动作/目标、变更及清空、来源模式、候选 ID、expected_context_version/revision；不包含会变化的当前时间/当前上下文状态。已有成功请求同参数重放时，先重验当前结果访问权，再返回持久化结果，**不要求临时上下文仍存在**；同键异参拒绝。
3. 对新的带来源请求，按第 5.5 节在同一上下文短临界区内核对操作者、有效会话、对象/客户、模板、expected_context_version、候选资格和真实选择，复制不可变来源包并冻结该上下文。此刻为来源选择接受点；TTL 在此刻检查。纯手工无来源请求不创建临时上下文，但仍执行以下相同业务保护。
4. 在一个业务事务内按定版锁顺序重读记录。更新无条件校验数据库当前接案、当前客户及动作权限，即使正文没有 client_id；若允许改绑，再检查原对象/原客户和目标客户/改绑权限。创建校验目标客户和创建权。检查本次已锁定版本、允许状态、expected_revision、实际字段变更、子项/来源保护；不能使用事务外旧客户授权结果替代。
5. 原子保存草稿、当前逐字段来源关联、必要不可变快照及原生幂等结果。带来源时回执记录接受的 context_version 和实际逐字段候选/覆盖状态；数据库任一步失败整体回滚，不先成功再补来源。
6. 提交成功后结束旧上下文，返回真实 ID、revision、saved_at、来源引用/覆盖及已接受口径版本。前端只据此更新保存状态；原菜单读取同一服务端对象。确认未提交、回滚或结果不明确时，分别按第 5.5、10.2 节处理，不将所有错误一律视为可换键重试。

锁顺序待 I0 对照实际数据库定版，初步为原生请求占位 → 必要客户保护 → 接案 → 受影响子记录 → 来源关联/快照。若为锁客户而先读取客户 ID，取得接案锁后必须核对该 ID 和版本仍一致；不一致时中止并重新核对，不能沿用旧客户权限或临时追加逆序锁。创建跳过不存在的接案锁。原生请求占位用于业务幂等，不是通用助手运行表。

上下文锁不跨数据库 I/O 或模型调用；业务事务不调用模型。复制后的来源包独立于内存 TTL 清理，但不豁免事务内授权、状态和版本。并发同键在原生唯一约束及请求协调下只产生一个成功结果；没有结果尚不能证明未提交。

权限以事务内最终业务授权检查为本次办理判断点；该检查前已经生效的撤权必须拒绝。更强的“并发撤权提交必定压过全部在途保存”需要统一授权并发协议，本稿不宣称具备。读取回执、当前/历史来源时仍按当前权限重新授权。

### 10.2 必须区分的重复请求

| 情况 | 结果 |
|---|---|
| 双击/网络重试，同账号、同动作、同键同参数 | 返回同一保存结果，不新增草稿、来源版本或副作用 |
| 同键不同参数 | 拒绝并提示这是不同保存，不能返回旧成功掩盖新内容未保存 |
| 不同账号同样的键 | 不能相互读到结果；按作用域隔离，旧全局唯一索引兼容需验证 |
| 创建/更新已提交但响应丢失 | 查询本人原请求结果或以同键重试；未查到不证明没提交，不能换键再创建 |
| 回执已存在，但上下文过期/进程重启 | 持久化结果仍可读；按当前访问权返回，不能重新创建 |
| 新保存需要来源，但上下文已丢失 | 拒绝这次来源保存；保留表单，可重新整理或明确转为人工无关联来源保存，不暗中丢弃来源 |

数据库缺少 revision、来源约束或所需幂等保护时，带来源的保存失败关闭；不得 tableExists 为假就跳过落库并返回成功。页面“已应用”“已保存”“来源未关联”必须分别显示。

## 11. 最小技术方案与接口契约

### 11.1 组件边界

继续使用 Go 单体及 React 原页面。建议新增小范围的接案整理服务、来源服务和前端侧栏/合并工具；原生创建/更新的必要业务规则归入同一接案应用服务。保留完整字段限制、客户授权、身份保护、所有权和原有事实失效语义，不把 handler 原样包装成模型工具。

模型只有文本输入/结构化候选输出，无保存、网络查询、身份确认、检测或审批工具。后续 MCP 不作为本批前置。临时上下文建议为 Go 内存中的有界对象，不进入通用缓存或 Elasticsearch；若部署实际多实例，必须重新评审最小共享临时存储或试点拓扑，不能部署后靠碰运气命中同一实例。

~~~mermaid
flowchart LR
    P[原生接案页面] -->|描述与补充| C[临时整理上下文]
    C -->|必要文字与模板| M[模型]
    M -->|结构化候选| C
    C --> R[事实、来源和差异卡]
    R -->|律师选择应用| P
    P -->|原生保存| S[接案应用服务]
    C -.->|服务端解析选中出处| S
    S -->|同一事务| D[草稿、来源快照、原生结果]
    D -->|原菜单重新读取| P
~~~

### 11.2 临时上下文的最小内容和生命周期

保存 actor/session 绑定、随机 context_id、context_version、对象/客户/模板、源 revision、被接受的用户轮次、来源片段、律师的口径/不纳入选择、有限候选及资格、当前保存键/冻结状态和请求去重信息。仅在进程内暂存；不落普通日志、localStorage、sessionStorage、IndexedDB 或分析埋点。现有本地草稿不得扩展包含这些内容；已应用的标题/摘要可能进入现有本地草稿，其存储范围和旧副本恢复必须单独核验。

上下文内保留本次有限轮次生成的不可变候选，最多与 8 轮上限相同；界面默认展示最新一份，但不能覆盖掉已应用字段关联的前轮候选。标题和摘要可以来自不同轮次，来源选择必须逐字段带 candidate_id。旧候选若被后续已选更正影响，按第 5.3 节标记口径过期；保留记录不代表继续允许不经核对应用。

待确认的原生保存可在当前账号范围内短期保存无内容的 request_id、动作类型等最小查询标识，用于刷新后先查结果；不能将正文、来源包或认证令牌一并持久化。刷新后若无法重建完全相同的请求，只查询原请求，不伪造同键新参数。查询仍不确定时不得自动换键新建；需等原请求结果明确或人工核实后再处理，本批不承诺恢复丢失的未保存对话。

建议初始预算（配置值待 I0/真实模型测定）：

| 项目 | 建议上限 | 超限行为 |
|---|---|---|
| 每轮用户输入 | 6,000 code points | 提示拆分/删减，不截断成另一事实 |
| 单上下文总用户输入 | 20,000 code points | 停止新增模型调用，允许原生人工整理 |
| 用户轮数 | 最多 8 个接受动作，文字/口径/不纳入提交均计入；同 request_id 重放不计 | 一次提交可合并多个选择；显示剩余轮次，建议结束本次，不强制补齐 |
| 单用户活动上下文/模型请求 | 各 1 个 | 提供结束本人旧整理的中性选项，不泄露旧对象标题 |
| 单部署活动上下文/模型并发 | 32 / 2 | 明确限流，无无界排队 |
| 单轮总时长 | 45 秒，最多一次格式修复计入同一预算 | 超时中断，不自动恢复或写业务 |
| 单上下文模型累计时长 | 180 秒 | 停止模型，保留可用候选供人工核对 |
| 临时上下文 TTL | 空闲 30 分钟、绝对 2 小时 | 清理未保存对话；已保存业务来源不受影响 |

同一轮 request_id 同参数（含动作、正文及预期版本）在上下文存续期内先按去重记录返回同一结果，不因当前版本已推进再接收一遍；同键异参拒绝。新轮必须检查 expected_context_version，快速双发不默认排队或自动重放。模型调用同步随请求执行，断连/取消传递取消信号；仍计入占用直到实际结束或超时。不能把页面停止动画当作提供方已停止处理/计费。旧响应、过期 generation_id 或已结束对象不得再次显示为可应用。临时上下文丢失后不重建为旧状态，不承诺恢复未保存聊天。

## 12. 内容保护、模型外发和日志

### 12.1 最小外发

默认只发送当前上下文经接受的必要文字、固定模板和最小事实结构。现有 title/description 仅经用户选择纳入；客户证件、登录令牌、数据库信息、主体/材料数组、其他案件及权限配置不进入模型。模型输入中的“忽略限制、帮我审批、这个 ID 是我的”等文字都作业务数据处理，服务端规则不受其改变。

真实模型的首次技术评测只用虚构资料。真实律师先用模拟任务。若进入授权真实资料试用，必须明确提供方/部署、数据接收范围、服务商训练/保留配置、访问人员、来源保留及备份政策和退出处理。这些是实际数据使用条件；本稿不作法律许可结论，也不替律所同意向未知服务商发送案情。

### 12.2 日志边界

助手上下文、原生保存的 source_selection/摘要及来源读取路径，均须在读取正文之前设定内容禁记。检查范围覆盖应用日志、异常堆栈、代理、模型适配器、HTTP 重试/调试及前端分析。请求体、提示词、响应全文、原文片段不得进入普通日志；错误不能拼接正文。URL/query 不放案情或令牌。

允许记录：不带内容的请求关联 ID、动作、时长、长度、错误类别、计数、模型配置版本及预算。业务来源本身存入受控业务记录，不用日志替代。来源响应采用私有不缓存/禁止共享缓存策略，不能因 CDN 或通用缓存绕过撤权。

### 12.3 验证方法

使用唯一虚构标记分别放入短/长输入、模型异常、候选、原生保存、来源读取及错误路径，搜索实际挂载链和代理日志；不能只测试未挂载 audit.go。对正常页面本地草稿与临时来源分别检查浏览器存储，不把“身份号码没落 localStorage”推断为“全部新增内容都没落”。

## 15. 产品试用与指标定义

### 15.1 试用安排

建议 5～8 名实际目标律师，累计至少 24 个成对任务，即至少 48 次任务执行。一对由同一律师完成两份难度相近、事实不同的虚构场景：一份用原菜单，一份用助手。顺序交叉/随机，避免同一案情先做一次后凭记忆造成虚假提速。每人先完成不计分的熟悉任务。

20+10 技术任务与 24 对产品任务职责不同，不能将作者重复运行或同一人试跑计为真实用户样本。根据实际收案频率判断试点是否值得继续，不以聊天消息数作为成功指标。

### 15.2 时间、质量和采用

- 主动操作时间：从开始阅读材料、录入、对话、核对来源、修改、应用、保存到菜单重开完成的人工操作时间，含纠错和恢复。
- 总耗时：相同起止点的墙钟时间，包含模型/网络等待。两种时间分别报告，不能只算生成速度。
- 每对改善率 =（原菜单主动时间 − 助手主动时间）÷ 原菜单主动时间；报告各对中位数、每名律师中位数和原始分布，不用两个总体中位数相除冒充配对改善率。
- 质量：由独立评阅人按预先冻结的标准答案评价关键事实准确、完整性、未知/冲突表达、出处支持及人工不纳入是否合理；记录遗漏和补录负担，尽量不知使用方式。原始候选、人工改后及实际保存结果分别评分，不能用律师重写后的正确结果反推模型原先可用。先看质量，再看节时。
- 采用：记录是否应用标题/摘要、放弃原因、人工改动和来源覆盖。候选文字保留率只作描述，不单独作为质量或继续投入门槛。

### 15.3 建议裁定线

以下为需要业务负责人校准的探索性目标，不是经数据证明的行业标准或统计保证。

| 裁定 | 建议条件 |
|---|---|
| GO：继续小步投入 | 技术门禁全部通过且无严重事件；结果质量不下降、关键事实无未处理严重错误或无说明遗漏；配对主动时间中位改善以 30% 为目标，同时总耗时可接受；多数律师愿在相同任务继续使用且理由具体 |
| CONDITIONAL GO：修正后再测 | 安全和原生一致性通过；时间收益 10%～30% 或因等待偏长，但缺项/核对收益明确；只迭代已定位瓶颈，不并行开平台项目 |
| STOP/重新定位 | 越权、泄漏、错对象、静默覆盖、重复保存或伪造来源；或核对负担使质量/总耗时明显变差且无清楚改善路径 |

可附带统计缺项“有用”的比例（探索目标 70%）、错误/重复提醒数量、愿继续使用人数及原话。分母必须是实际产生且被评价的提醒/参与者，未知评价不能当有用。小样本只用于下一步决策，不外推全所或全市场效率。

## 16. 关闭、故障与回退

使用一个助手生成启停开关和试用人员白名单即可起步；关闭后停止新整理，原生菜单及经授权的已保存来源仍可用。模型失败不清空表单。已经应用但未保存的字段不自动删除；是否人工保存及来源是否仍有效要如实提示。

前端取消只结束临时整理，不撤销已经提交的原生保存。保存结果不明时查同一请求；已成功保存需走原生编辑修正，不删除草稿假装回滚。

数据库变更采用兼容扩展及回滚准备，必须核对实际方言、旧索引与旧客户端；停用助手不等于可以直接删 revision、幂等结果或来源表。真实迁移、部署、权限/凭据变化和真实资料使用均需另行具体授权。本稿只要求准备和验证方案。
