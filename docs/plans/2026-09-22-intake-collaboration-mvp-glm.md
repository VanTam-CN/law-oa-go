# 下一轮改造方案：接案协作 MVP（GLM 执行版）

日期：2026-09-22。版本：v1.0。历史方案于2026-11-07按既有授权由Codex实施；[最终工程报告](../../reports/evidence/intake-collaboration-mvp/20261107/final-report.md)记录当前状态。真人试用及生产验收未执行；下文保留原GLM方案要求，不代表本轮由GLM执行。

本轮目标：律师在登记新客户、等待复核、收到退回、补充重提的过程中，能够保留工作上下文，从自己的工作台直接找到下一步，并最终生成唯一、资料一致的正式案件。

本文是主方案；配套 [OpenSpec 提案](../../openspec/changes/add-intake-collaboration-mvp/proposal.md)、[实施清单](../../openspec/changes/add-intake-collaboration-mvp/tasks.md)和规格用于 GLM 跟踪执行。用户将本文交给 GLM 并明确要求执行后，即按此范围开展本地实现和必要验证，不在每个批次后例行重复索要许可。本次编制方案没有修改业务代码，也没有代替用户启动 GLM。

## 1. 目标与交付范围

### 1.1 要解决的业务问题

1. 新客户尚未建档时，律师必须离开立案页，登记后再回来选择。
2. 接案、冲突、审批、待办各有页面，但用户仍需自己判断下一步去哪里、由谁处理。
3. 退回意见主要是文字，申请人需要自己找到字段；重提还必须确保新事实、新检测、新审批依据一致。
4. 草稿恢复已有能力，但入口、保存反馈、操作手册与不同候选版本尚需统一。

### 1.2 本轮成功的定义

在隔离 PostgreSQL 和全虚构资料下，一条案件链通过正常页面完成：

> 登录 → 新建立案 → 原地新增客户并选中 → 保存退出 → 重登继续草稿 → 正式检测与独立复核 → 提交接案审批 → 审批人提出两项补充要求 → 律师从待办进入原申请并完成修改 → 按规则重新检测及复核 → 原审批重新提交 → 审批通过 → 自动形成唯一案件 → 双方待办与实际业务状态一致。

“完成”同时包含页面可操作、服务端校验、持久化一致、权限隔离、失败恢复五个维度。接口成功或按钮可点都不能单独证明闭环完成。

### 1.3 明确纳入

| 编号 | 交付 | 必须具有的行为 |
|---|---|---|
| G1 | 立案内新增客户 | 原地打开表单、复用客户服务、成功回填、失败保留当前立案 |
| G2 | 可办理的个人待办 | 每项显示事项、处理人、阻塞原因和动作；点击进入正确业务对象 |
| G3 | 结构化退回补充 | 补充项清单、字段定位、逐项回复、服务端核验和原审批重提 |
| G4 | 草稿与工作台衔接 | 首页可继续已有草稿；明确未保存/保存中/已保存/保存失败 |
| G5 | 同版本手册与证据 | 手册步骤、截图、运行前后端、测试报告对应同一候选 |

### 1.4 明确后置

本轮不做完整文档中心、立案附件上传扩展、在线编辑、全文检索、财务收费、案件日历、自动计算法律期限、批量导入、短信/邮件/微信催办、原生手机应用、通用工作流引擎或全站界面重构。代管款等既有模块不扩展。

“初查带入立案”属于后续体验增强：本轮保留初查不保存、不能代替正式检测的边界，不新建咨询线索库，不把初查结果升级为正式结论。真实律师评价可在工程交付后开展，但不允许代理模拟其满意度。

## 3. 用户旅程与页面规则

### 3.1 律师

工作台首屏优先展示“需要我处理”“等待他人”“继续草稿”。新建接案与初查保留入口，初查表单默认折叠；统计下移，不删除现有信息。

打开立案后，在客户选择器旁使用“新增客户”。创建成功后客户自动选中，案件名称、对方、共同委托人、其他相关方、业务字段和当前步骤全部保留。未保存状态要准确显示；客户建档成功不等于立案已经保存。

收到退回时，在“需要我处理”看到“某申请待补充 2 项”。进入后页首显示退回人、时间、原意见、缺项清单；点一项定位对应字段。完成后检查逐项回复及修改摘要，必要时重新检测并完成独立复核，再点击“补充完成并重新提交”。

### 3.2 核查人与审批人

核查人看到自己有权处理的任务，并沿用已有独立核查流程。业务审批人从自己的待办进入审批，先看本轮提交版本和修改摘要，再作决定。

本轮结构化退回作用于已有 `ApprovalDecisionRequest` 支持的审批决定路径。独立核查专用接口不凭本方案新增另一套退回状态；核查岗能否在某审批节点作决定，仍由既有授权确定。

### 3.3 助理及其他角色

助理保留当前允许的摘要/材料清单协作范围，不能因新增入口而录入受限制主体、确认事实、运行正式检测或代律师提交。新增客户入口必须同时满足当前页接案权限和客户创建权限。冲突核查岗、普通用户、财务账号也不得因有待办而取得接案写权限。

未指派处理人时显示“待分配”及现有有权角色的处理入口，不显示“已经通知某人”。等待事项与需要本人处理的事项分开，禁止同一条记录被同时计入两类。

## 4. G1：原地新增客户

### 4.1 表单和交互

- 使用现有 Modal/Drawer 模式，字段沿用客户主档案契约。最低包含名称、个人/企业类型、匹配的身份类型与号码；电话、邮箱等按现有规则选填。
- 抽取客户表单及请求适配供客户页和立案页共用，不复制两份不一致校验；只拆本次相关部分，不整体重写 Batch01 大文件。
- 关闭弹窗不创建客户，也不清空立案。请求期间防止重复点击；失败保留弹窗内容并显示可恢复错误，身份原文只留在当前内存表单。
- 成功使用服务端返回的客户 ID 回填，不依赖“重新取第一页 50 条正好包含新客户”。选择器支持服务端授权搜索和分页，覆盖超过 50 个客户的情况。
- 修改已参与检测的客户必须走既有事实变更和检测失效规则。不能只替换前端名称而保留旧检测可提交状态。
- 若客户创建成功、后续立案保存失败，提示“客户已建档，立案尚未保存”；重试复用该客户 ID，不自动删除客户或再建一条。
- 同一次创建的响应尚不确定时保留原 key 重试；已明确取消或改为另一份创建请求才生成新 key。成功或明确关闭弹窗后清理弹窗内的身份原文，不写入 URL、浏览器历史或持久缓存。

### 4.2 请求一致性

复用 `POST /api/v1/clients`，不放宽 CanCreateClient 与身份保护。新增可选 `Idempotency-Key`：作用域为操作者 + 创建客户操作 + key。同 key 同规范化请求返回同一客户；同 key 不同请求返回 409。响应丢失后必须能用原 key 重试。

优先复用基线既有持久化幂等设施；若只存在接案专用实现，抽取最小共用能力或增加窄表 `client_creation_requests`，不要建立通用分布式框架。幂等记录、客户创建同事务；请求指纹不得保存身份原文或对低熵身份作可枚举的裸哈希，沿用受保护摘要/HMAC 机制；记录持久化结果 ID，不保存明文请求。

key 只表示同一次创建请求，不是主体身份。不同 key 的同名请求不得自动合并；同名不同身份仍是不同主体。已有客户去重规则继续执行，受限客户存在性不能通过错误返回泄漏。明确区分“请求重试防重复”与“全所主体去重”。

## 5. G2：待办与工作台直达办理

### 5.1 统一动作描述

定义小型 DTO `WorkflowAction`，工作台、待办列表、审批详情共用，以下是拟新增契约而非现有字段：

```text
resource_type: intake | conflict | approval | case
resource_id: string
action_code: resume_intake | review_conflict | decide_approval | supplement | view_only
action_label: 面向用户的中文动作
workflow_status: 真实业务状态
assigned_to: 当前有权查看的处理人摘要，可空
blocked_code / blocked_reason: 不可办理原因，可空
completion_mode: workflow | manual | legacy_unresolved
action_version: 服务端版本/节点标识，用于过期动作检测
```

服务端先做对象级授权，再生成动作。前端只按白名单映射内部路由，不接受任意跳转 URL。跳转后页面必须重新读取状态和权限，不能把待办 DTO 当授权凭证。无权对象不返回名称、当事人、补充意见或目标 ID。

completion_mode、workflow_task_key、系统来源引用和指派由服务端生成，普通待办创建/更新接口不能把业务任务改成 manual，不能借自建待办获得对关联对象的访问权。所有读写接口均需覆盖此限制。

### 5.2 来源编号兼容

保留 inbox_items.source_id 数字字段，新增可空字符串 `source_ref`，存放审批/冲突等真实业务 ID；响应 resource_id 统一字符串。新增协作待办优先使用 source_ref。不能把 UUID 截断、转为 0 后猜测目标，也不能从标题解析编号。

旧数字来源仅在关联类型及真实对象可验证时映射。无法确认关联的历史项返回 legacy_unresolved，显示“历史事项，关联对象待确认”，不提供可能指错对象的业务按钮。此类通知允许以“归档提醒”收起，但不影响真实业务状态，且不统计为业务完成。

### 5.3 可靠产生与完成

本轮建立一个窄的事务内协作待办写入函数，覆盖正式复核任务就绪/指派、审批提交、下一节点、退回、重提、终态。由现有业务转移点调用；不使用目前仅打印日志的 sendApprovalNotification 充当证据，不依赖未核实的 EventDispatcher 来源映射。

幂等键采用“业务类型 + 对象 ID + 轮次/节点 + 接收人 + 待办用途”，服务端生成，并用非空键唯一索引保证重试不重复。相同用户在同一轮收到审批结果通知和办理任务时须用用途区分。

业务状态、原任务关闭、新任务创建应在同一数据库事务完成；待办写入失败不得返回交接成功。不得在持有行锁时同步调用邮件等外部服务。本轮只做站内任务，无外部发送。

对无法立即事务化的历史入口，在 N0 列为前置依赖并补齐，不以“下次刷新再说”绕过。提供只针对本轮受支持对象的可重试补建函数，由服务端验证状态和幂等键；不在 GET 中偷偷改库，不全量改写历史待办。

### 5.4 “完成”与“延后”的语义

- workflow 类待办：只有真实业务转移才能完成；直接调用 complete API 必须返回明确 409，删除接口也不能删除仍需办理的任务。
- manual 类：仅明确登记为个人任务/提醒的事项可直接完成。不能笼统把所有 source_type=task 视为个人任务，EventDispatcher 也会用 task 表示系统事项。
- legacy_unresolved：只允许归档提醒，不伪造业务完成。
- 延后只改变提醒时间，不改审批期限、状态、责任人；“需要我处理”仍能找到被延后的未办事项。
- 审批通过但成案失败：审批处理任务可结束，案件创建必须显示失败/可重试的独立状态，不能显示“已成案”。
- 当前处理人更换后，原办理入口立即失去写权限；原待办标明已转交，新待办归新处理人，保留审计。

计数、筛选、列表都先按权限过滤再分页。已完成、等待他人、待本人办理的口径共用服务端规则；不靠前端取第一页后统计全量，也不逐条查询造成 N+1。

## 6. G3：结构化退回与版本化重提

### 6.1 退回清单

复用 ApprovalRecord.ImposedRequirements 的 JSON 存储，定义带 schema_version 的 `supplement_requests`，不覆盖原审批意见。每项由服务端生成稳定 item_id，包含 category、field_key、可选 party_local_id、说明、required。

本轮 category 白名单为 `field_correction`、`identity_verification`、`matter_explanation`。field_key 映射已支持的客户、当事人、事项摘要、案件类型/领域、负责律师等输入；多方定位使用稳定 localId，不用数组下标或名称。清单建议限制 1—20 项、每项说明不超过 1000 字；最终长度与现有接口约束取更严格者。

新入口退回至少一项且必须有审批意见。身份项只写“需核验某主体身份”，不把号码或受限命中详情写入普通清单。客户端不能提交任意字段路径、HTML 或外链来控制页面。

材料上传不在本轮：不增加“上传完成即可重提”的虚假动作。确需实体材料且当前无法收集的业务，显示尚缺能力并保持未满足，不用勾选框伪装材料已收齐。

旧记录只有文字意见时，以“历史补充说明”显示，要求填写回复；不伪造曾经存在的结构化项。新 UI 与旧调用方兼容时，允许把有效文字退回规范化为一条一般说明，标注来源 legacy_text，业务记录原文保持不变。

### 6.2 恢复与逐项回复

新增导航契约 `/case/create?intake_id=<id>&approval_id=<id>&mode=revision`。这只是定位信息：服务端必须验证审批属于该接案、当前用户是有权申请人、状态允许修改，不能信任 URL。

页面加载服务端接案事实与最新退回记录，复用既有草稿恢复和 revision 冲突保护。客户、相关方、角色、深度、标签等必须完整恢复；身份原文不回传，不用空值或掩码覆盖已保护身份。

逐项回复保存于接案的受控协作字段，关联 `return_record_id + item_id`，沿用 expected_revision 更新；服务端白名单合并，不开放任意 metadata 覆盖。仅保存回复不改变正式冲突事实版本语义；若现有草稿 revision 会递增，必须区分并验证业务事实版本/指纹与写入版本，不把回复存储误判为主体变更。

“已补充”只是申请人声明。服务端重新验证实际字段、身份保护状态、对应条目、授权与检测结论；审批人保留最终审核权。不存在/已删除主体的 field_key 需明确标记，不跳转到别人的相邻字段。

### 6.3 本轮提交的唯一权威依据

优先复用 approval_snapshots，新增受管理的快照类型 `intake_submission`，按 approval_request_id + snapshot_type + source_version 建唯一约束。只为新类型建立受控唯一约束，不能删除旧重复快照来让迁移通过。

approval_requests 增加可空 `active_submission_snapshot_id`，明确指向当前提交依据。新类型快照至少包含：审批/接案 ID、接案事实版本、正式检测 ID、独立复核依据、结构化事实、补充清单与回复、本轮序号、提交人/时间、上一轮快照 ID、最新退回记录 ID。

旧 metadata.approval_snapshot 和旧快照行保持原样。第一次进入新协议时，只有能够验证的旧快照才建立兼容映射；来源冲突或无法确认则阻止该条重提并显示具体原因，不通过猜测最新草稿补写历史事实。

建立统一服务端快照读取方法：审批详情、snapshot API、决定校验、integration 状态、自动成案、失败重试和主体物化必须读取同一 active 指针。禁止一处取 created_at 最新快照、另一处取旧 metadata。旧调用方需要的顶层 conflict_check_id 等字段由当前权威快照生成或在同事务更新，历史快照不改写。

每条新审批决定记录保存其实际依据的快照/轮次与节点标识。普通审批更新、接案 metadata 更新及通用 submit/resubmit 入口不能接受客户端覆盖 active 指针、审核结果或检测绑定；接案审批必须进入统一受控路径，旧调用方也不能绕过。审批已通过后锁定其依据，失败成案重试仍使用批准时版本。

### 6.4 重新检测规则

| 改动 | 正式检查要求 |
|---|---|
| 客户、对方/相关方、身份、角色、关系/穿透、负责团队或既有指纹中的事实变化 | 旧结果不可继续提交；保存并确认新事实，重新检测并完成既定独立复核 |
| 只补充回复说明，未改正式事实 | 服务端确认事实与检测绑定仍一致，且结果、覆盖范围、复核仍有效，才允许复用 |
| 字段影响不明、版本缺失、结果失效或检索范围不足 | 明确阻止继续或要求重检，不能默认无影响 |

不新增“律师自己勾选无需重检”能力，不用前端 fingerprint 代替后端门禁。已有独立复核、豁免、隔离墙条件继续执行。

### 6.5 原审批重提事务

扩展既有 resubmit 入口，接收 expected_intake_revision、expected_submission_snapshot_id、return_record_id、逐项回复及 revision_note；客户端不提供最终审批快照内容。

在统一锁顺序下锁定接案/审批，重新验证申请人、允许状态、最新退回轮次和事实版本；验证回复和当前正式检查/复核；取得既有接案审批唯一绑定；由服务端生成新快照、更新 active 指针及关联字段、按既有规则重新指派、转为 resubmitted、关闭旧补充任务并创建新审批任务，全部同事务提交。

冲突复核必须先满足既有检查门；业务重提重新走既有审批指派起点，不把上一轮对旧资料的通过节点自动沿用。未经用户另行确定，不改变审批级数或自审批限制。

同一 return_record_id 与同一规范化重提请求重放返回原轮次结果；不同内容的重复重放返回 409。迟到的旧页面 approve/reject/request_changes 必须带当前 snapshot/节点版本，服务端识别过期后拒绝，不能对新一轮生效。

保留 a806831 的原子重绑、唯一接案占槽、成案事务及所有权保护。两次请求同时重提，或原审批重提与新审批争用同接案，只能有一个有效持槽审批；失败方无新快照生效、无复活状态、无新待办。已成案申请不能以补充路径再创建案件。

已有拒绝/取消等终态继续遵守状态机，不能把所有终态都改为“可补充”。本轮新 UI 默认只为 needs_revision 提供补充入口。

## 13. 使用者验证与产品判断

工程检查通过后，再邀请 3—5 名试用者使用虚构案件；实施者的代理操作只作为工程可操作性证据。每人至少完成新客户接案、草稿恢复、退回补充三个任务。角色协作任务由不同账号和适格角色执行，不为了减少等待让同一人自审。

记录每项的完成/失败位置、主动操作时间、等待时间、求助次数、重复录入次数、找错入口次数。不要把审批等待计入律师填表操作时间。若有旧版基线可比，用相同任务和同类样本比较；没有基线就如实报告首次测量，不声称效率提升百分比。

本轮工程通过要求 C01—C18 必需项均有相应证据、无未关闭的权限/数据/主链路阻断；未做真实使用者试用时，产品可用性评价保持待验证。不能以平均通过率掩盖关键失败。

## 14. 风险、停止条件与回退

| 风险 | 控制 |
|---|---|
| 从较旧主树重做导致历史修复丢失 | N0 差异矩阵，以实际候选验证，不全目录覆盖 |
| 客户响应丢失导致重复创建 | 操作者范围的持久化幂等与同事务提交 |
| 待办显示完成但业务未完成 | completion_mode、服务端禁止直接完成、事务交接 |
| 新轮次审批读到旧检测或旧快照 | active 指针与统一读取；迟到决定版本校验 |
| 重提与新审批竞争生成两案 | 保留绑定唯一索引、统一锁序、事务回滚及并发专项 |
| 清单与修改摘要泄漏身份/隔离信息 | 服务端角色裁剪，结构化字段白名单，不回传身份原文 |
| 升级后退回旧程序误用历史快照 | 新记录需兼容读取版本；优先前向修复，不删审计回退 |

发现跨用户数据泄漏、主体误合并/丢失、假 completed、重复成案、覆盖历史快照时，停止受影响样本继续推进并保留现场；独立场景可继续。不得直接修改数据库把失败样本“修绿”。

本轮授权边界仅为用户交付 GLM 后的本地代码、迁移文件和隔离测试。生产发布、真实资料迁移、正式权限变更、对外发送、push/merge 仍需具体授权。`production_ready=false` 保持不变。普通本地可回退修复和必要复测在范围内持续完成，无须逐步询问。
