## 2. 迭代摘要

本次迭代只解决一个核心问题：让律所从“收到一个新案源”到“完成冲突判断并进入审批决策”形成可追踪、可留痕、可协作的闭环。

Batch 01 对应的产品链路是：

1. 工作台识别今日优先事项
2. 从客户主档案补齐主体信息与关联方
3. 在接案工作台完成案件录入与资料完整度检查
4. 对拟代理客户、对方当事人、关联实体和历史事项执行利益冲突检查
5. 将冲突结果联动到审批流程，形成准入决策

本迭代不追求覆盖所有后台模块，而是优先把“接案前风控”做成系统主卖点。

## 3. 背景与问题定义

当前系统已经具备客户、案件、冲突、审批等独立能力，也已有前端页面与后端接口，但用户视角仍存在以下问题：

- 接案动作分散在多个页面，用户需要自己拼接流程
- 客户主数据、对方当事人、关联实体的检查动作缺少统一入口
- 冲突结果虽然能输出命中，但与审批和案件准入的联动表达仍不够强
- 工作台对“今天必须处理什么”呈现不够聚焦，无法承担真正的指挥中心角色

本次迭代的目标不是重写底层能力，而是以 Batch 01 的页面和交互为载体，重组已有能力，形成对内可执行、对外可展示的主流程。

## 4. 目标与非目标

### 4.1 业务目标

- 将接案前关键流程收束为一个连续闭环，减少跨模块跳转成本
- 把客户建档、案件录入、冲突检查、审批联动统一纳入风控准入流程
- 让合规、负责律师、合伙人在同一链路中看到一致的数据与状态
- 将系统首页从信息看板提升为“待办驱动的操作入口”

### 4.2 用户目标

- 负责律师可以快速判断一个新事项能否进入正式立案流程
- 合规人员可以快速识别高风险命中，并给出处理建议
- 合伙人可以在审批页完成最终准入决策，而不是依赖线下沟通
- 助理和客户经理可以在前置环节补齐主数据，减少后续返工

### 4.3 非目标

- 不包含文档库、OnlyOffice、通知中心、财务管理、信托账户等 Batch 02-04 内容
- 不重做底层数据库模型和通用权限体系
- 不在本迭代内建设客户门户、移动端、聊天协作
- 不引入新的第三方工商数据服务采购决策，只使用现有系统能力和已有设计方向

## 5. 角色与核心场景

### 5.1 目标角色

- 负责律师：发起接案、查看冲突结果、提交审批
- 合规专员：复核冲突命中、给出风险意见
- 管理合伙人：做出最终审批决定
- 助理 / 客户经理：补齐客户主数据、维护关联方和对方当事人信息

### 5.2 关键场景

#### 场景 A：新客户咨询转正式接案

1. 律师在工作台看到“今日新增案件”和“待冲突复核”
2. 打开客户主档案，确认客户主体、联系人、股东及关联方信息
3. 进入接案工作台填写事项类型、对方当事人、负责律师、费用模式和基础摘要
4. 系统执行冲突检查，输出风险分级和证据链
5. 律师决定直接发起审批或补齐材料后重新检查

#### 场景 B：高风险冲突命中

1. 冲突结果页命中直接对立或高风险历史事项
2. 合规专员查看来源案件、命中范围、置信度和穿透层级
3. 若不可豁免，则建议拒绝承办；若可豁免，则进入审批链路
4. 审批页显示冲突摘要、附件、审批意见和 SLA 倒计时

#### 场景 C：管理层看当天风控负载

1. 管理合伙人在工作台查看待审批、待复核、逾期任务、在办案件总数
2. 快速进入高风险冲突与审批事项
3. 在审批页完成决策或退回补充

## 7. 功能需求

### 7.1 工作台指挥中心

#### 目标

把工作台从“静态指标页”升级为接案前闭环的第一入口。

#### 功能要求

- 顶部必须展示与接案闭环直接相关的核心指标：
  - 待办事项
  - 利益冲突待复核
  - 待审批事项
  - 今日新增案件
  - 在办案件总数
  - 逾期任务
  - 合同回款预警
- 主工作区必须支持以下内容：
  - 我的待办列表
  - 冲突复核提醒
  - 审批提醒
  - 逾期任务 TOP 列表
  - 最近活动
- 风险区块必须支持直接跳转到冲突检查结果页或审批详情页
- 页面应默认按“待处理优先级”排序，而不是按时间倒序平铺

#### 成功标准

- 用户无需进入二级菜单，即可发现当天最重要的接案前风险事项
- 用户可在 2 次点击内进入冲突页或审批页

### 7.2 客户主档案

#### 目标

在接案前先确认客户主数据的完整性，降低误检和漏检。

#### 功能要求

- 支持查看企业客户基础信息：
  - 客户名称
  - 别名 / 历史名称
  - 法定代表人
  - 股东 / 董事 / 高管
  - 联系人
  - 风险标签
  - 资料完整度
- 支持查看关联方：
  - 母子公司
  - 持股实体
  - 关联基金 / 控股平台
  - 历史事项关联实体
- 支持查看历史委托和关联案件
- 支持从客户档案发起“新建案件”或“重新执行冲突检查”
- 若资料完整度低于阈值，页面必须提示用户先补全再进入冲突检查
- 资料完整度默认由后端计算并返回，前端仅负责展示缺失项与阻断提示，不自行定义规则
- 客户档案编辑必须带版本号或等价乐观锁标识，避免多人同时编辑导致后提交覆盖前提交

#### 成功标准

- 用户能在一个页面内判断客户主数据是否足以支撑冲突检查
- 客户档案成为接案前的事实来源，而非单纯展示页

### 7.3 接案工作台

#### 目标

让案件录入、团队分配和冲突触发在同一个工作面完成。

#### 功能要求

- 页面以分段式表单承载以下信息：
  - 客户
  - 对方当事人
  - 案件类型
  - 业务领域
  - 负责人 / 协办团队
  - 费用模式
  - 案件摘要
  - 附件与材料清单
- 必须显示资料完整度与缺失项
- 必须支持“保存草稿”和“保存并检查冲突”
- 增强案件接口需要支持在案件创建后直接触发冲突检查
- 如果对方当事人、客户或关联实体为空，则禁止进入正式冲突检查

#### 成功标准

- 律师与助理可以在一个页面完成可检查状态的案件录入
- 提交后不需要手动再进入单独模块做第一次冲突检查

### 7.4 利益冲突检查结果

#### 目标

将冲突检查从“命中列表”升级为“风险判断工作面”。

#### 功能要求

- 查询摘要区必须展示：
  - 拟承办案件
  - 客户 / 委托人
  - 对方当事人
  - 关联律师人数
  - 检测范围
  - 检测耗时
- 结果区必须至少区分以下类型：
  - 高风险
  - 中风险
  - 低风险
  - 提示
- 每条命中必须展示：
  - 命中主体
  - 命中类型
  - 命中范围
  - 置信度
  - 穿透层级
  - 证据摘要
  - 来源案件 / 来源库
- 页面必须突出以下专项能力：
  - 三层递归穿透
  - 风险评分
  - 合规建议
  - 豁免可能性评估
- 结果页必须提供行动按钮：
  - 发起冲突审批
  - 申请豁免评估
  - 调整团队律师
  - 退出案件
- 冲突检查默认按异步任务设计：
  - 创建检查任务后立即返回任务 ID
  - 工作台、接案工作台和结果页都可查看检测进度
  - 前端通过轮询获取状态；后续可扩展 SSE，但本迭代先以轮询为准
- 若检测任务耗时较长，用户可离开当前页，系统应在工作台和待办区提示“后台检测中”

#### 成功标准

- 合规专员无需导出报告，也能直接给出处理建议
- 律师可以从结果页直达审批流程，不需要线下转述风险

### 7.5 冲突联动审批

#### 目标

让审批页承接冲突结论，形成准入决策闭环。

#### 功能要求

- 审批页必须展示：
  - 流程节点
  - 当前审批人
  - SLA 倒计时
  - 申请摘要
  - 冲突摘要
  - 风险意见
  - 附件
  - 历史意见流
- 审批操作必须包含：
  - 通过
  - 驳回
  - 退回补充
  - 重新提交
  - 取消
- 若用户点击“申请豁免评估”，必须进入单独的豁免子流程：
  - 填写豁免理由
  - 补充豁免依据与附件
  - 指定审批人
  - 形成 `豁免评估中 -> 豁免通过 / 豁免拒绝` 的状态流转
- 审批提交时必须固化快照：
  - 冲突结果 JSON 快照
  - 风险评分与证据摘要
  - 申请时的客户、案件、对方当事人关键字段
  - 可选 PDF / 报告文件引用
- 审批详情页默认展示“审批提交时快照”，而不是最新实时数据；若底层数据后续发生变化，应明确标识“源数据已更新，不影响审批快照”
- 当审批通过且系统状态满足条件时，必须支持后续案件创建联动
- 审批页需要和集成接口保持一致，确保“带冲突检测的审批”状态可查询、可重试、可取消

#### 成功标准

- 合伙人在审批页即可完成是否承办的决策
- 冲突检查不再是独立动作，而是正式准入流程的一部分

## 8. 用户流程

### 8.1 主流程

1. 用户进入工作台
2. 从工作台进入客户主档案或接案工作台
3. 补齐客户与案件信息
4. 触发冲突检查
5. 在结果页查看命中与建议
6. 如需决策则发起审批
7. 审批通过后进入案件准入后续动作

### 8.2 失败与异常流程

- 客户资料不完整：停留在客户档案或接案工作台补齐资料
- 冲突命中不可豁免：结果页建议退出案件，不进入正常审批链路
- 审批被退回：返回接案工作台或客户档案补充资料后重新提交
- 集成链路失败：在集成状态页或审批页提示重试 / 取消
- 冲突检查耗时过长：检查任务转为后台执行，用户返回工作台查看进度与结果
- 助理补齐资料后：系统必须向负责律师或合规专员发出正向移交通知，而不是仅停留在“已补充”状态

## 9. 信息架构与页面关系

### 9.1 页面关系

- 工作台 -> 客户主档案
- 工作台 -> 接案工作台
- 工作台 -> 冲突结果

- 接案工作台 -> 冲突结果
- 冲突结果 -> 审批详情

### 9.2 导航原则

- Batch 01 的 5 个页面必须形成闭环跳转，不依赖用户手动回到左侧导航重新找入口
- 高风险与待审批事项必须始终可从工作台返回查看

### 10.2 数据约束

- 客户、对方当事人、案件类型为冲突检查的必填前置条件
- 关联实体和历史事项应作为冲突判断的默认范围
- 冲突结果必须保留检查历史，供工作台与审批查询
- 审批状态与冲突状态必须能相互引用，避免数据孤岛
- 冲突提交审批后必须生成不可变快照，后续源数据更新不得直接覆盖审批展示内容
- 客户主档案更新与审批提交都必须具备防重提交与并发保护机制

### 10.3 异步与并发约束

- 冲突检查为异步任务：
  - `queued`
  - `running`
  - `completed`
  - `failed`
- 前端默认轮询任务状态，建议间隔 2-5 秒
- 若任务失败，必须返回失败原因和重试入口
- 客户主档案更新必须带 `version` 或等价字段；版本不匹配时返回冲突错误
- 审批提交必须带防重 Token，避免重复点击生成重复审批实例

## 11. 页面级交互与状态要求

### 11.1 统一状态

- 草稿
- 待检查
- 检查中
- 检查失败
- 已命中
- 待审批
- 审批中
- 待补资料
- 已移交
- 豁免评估中
- 豁免通过
- 豁免拒绝
- 已通过
- 已驳回
- 已退出

### 11.2 统一反馈

- 所有阻断性错误必须明确告诉用户“缺什么数据”
- 所有高风险命中必须带原因与建议动作
- 所有审批阻塞都必须带当前节点和剩余 SLA
- 所有并发覆盖风险必须明确提示“数据已被他人更新，请刷新后重试”
- 所有异步检测都必须可见当前状态、最近更新时间和下一步动作

## 12. 指标与验收

### 12.1 业务指标

- 新事项从录入到完成首次冲突检查的平均耗时下降
- 高风险事项进入审批的平均响应时间下降
- 因客户资料不全导致的重复检查次数下降

### 12.2 产品指标

- Batch 01 的 5 个页面形成闭环跳转
- 工作台可直接进入冲突和审批详情
- 用户在接案工作台提交后可一键触发冲突检查
- 冲突结果页可直接发起审批
- 客户主档案页可直接依赖客户域接口完成渲染
- 后台检测中场景可在工作台追踪，不要求用户停留在结果页等待
- 助理补齐资料后可成功创建正向移交通知

### 12.3 验收标准

- 工作台、客户、接案、冲突、审批 5 页在信息结构上与 Batch 01 样例图一致
- 所有关键动作均能映射到现有接口或本迭代目标补齐接口
- 冲突检查和审批联动链路可被完整演示
- 高风险、可豁免、需补资料三类场景均可在系统中表达
- 审批展示基于快照，底层数据变更不会污染历史审批上下文
- 客户并发编辑冲突和审批重复提交场景均有明确处理策略

## 13. 实施顺序建议

### 13.1 第一阶段：流程打通

- 统一工作台入口
- 客户档案与接案工作台联动
- 接案后触发冲突检查
- 冲突结果页接入审批入口

### 13.2 第二阶段：表达强化

- 工作台风险分组与优先级排序
- 冲突结果页证据链和建议区强化
- 审批页的冲突摘要与 SLA 表达强化

### 13.3 第三阶段：演示与验收

- 按 Batch 01 样例图统一视觉与布局
- 完成端到端演示脚本
- 以“新事项承办决策”作为标准验收场景

## 14. 依赖与风险

### 14.1 依赖

- 客户与案件基础数据质量
- 冲突检测服务的稳定性与结果可解释性
- 审批服务与集成服务状态一致性

### 14.2 风险

- 如果客户主数据不完整，冲突准确率会被拉低
- 如果结果页与审批页语义不一致，会导致线下补充沟通仍然大量存在
- 如果工作台只保留指标不保留动作入口，则无法承担主流程入口角色

## 15. 本迭代默认决策

- 默认以桌面端后台页面为唯一交付，不做移动端
- 默认优先使用增强案件与集成审批链路，而不是仅靠基础 CRUD 页面
- 默认 Batch 01 以“接案前风控闭环”作为第一优先级，而不是案件全生命周期管理
- 默认视觉与交互以 `reports/image2-feature-gallery` 中 Batch 01 样例图为参考基线
